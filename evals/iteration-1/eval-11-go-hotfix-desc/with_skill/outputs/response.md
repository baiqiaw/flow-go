## 热修流程启动

### 1. P 等级判定

**描述**：生产环境内存泄漏，每隔 2 小时 OOM 重启一次

**判定：P1（部分功能炸）**

理由：
- 服务仍在运行，但每隔 2 小时被 OOM Killer 重杀重启
- 不是完全不可用（区别于 P0），但严重影响生产稳定性
- 用户数据可能丢失、请求中断、SLA 受损
- 无需先回滚，可直接进入诊断修复

### 2. 根因分析（Iron Law — 无根因不修复）

**收集症状**：
- 现象：内存持续增长，约 2 小时触及 OOM 阈值被杀
- 复现条件：生产环境持续运行
- 关键特征：线性增长模式（非突发），典型内存泄漏

**需要收集的信息**：
1. 服务启动时的初始内存占用？
2. 内存增长是线性还是阶梯式？
3. 最近是否有部署变更？
4. 是否有 goroutine 泄漏的迹象（pprof goroutine count）？
5. 是否有大对象缓存在内存中未释放？

**常见根因假设（最多 3 个）**：

| # | 假设 | 验证方法 | 可能性 |
|---|------|---------|--------|
| H1 | goroutine 泄漏（每次请求创建但未退出） | `pprof goroutine` 查看协程数量是否线性增长 | 高 |
| H2 | 全局 map/slice 无限增长（缓存无淘汰） | `pprof heap` 查看 inuse_objects 按类型分布 | 高 |
| H3 | 连接/资源未关闭（DB连接/HTTP response body） | 代码审查 + `pprof heap` 查看按调用栈分配 | 中 |

**验证步骤**（需要用户提供或在线上执行）：

```bash
# 1. goroutine 数量检查（H1）
curl http://localhost:6060/debug/pprof/goroutine?debug=1 | head -50

# 2. heap profile（H2/H3）
curl http://localhost:6060/debug/pprof/heap > heap.prof
go tool pprof -top heap.prof

# 3. 30 秒内分配最多的调用栈
curl http://localhost:6060/debug/pprof/allocs > allocs.prof
go tool pprof -top allocs.prof
```
