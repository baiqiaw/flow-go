## 步骤 1 · P 等级判定

**Bug 描述**：支付接口超时，用户反馈支付时经常超时失败

**P 等级分析**：
- **P0（完全不可用）**：否。支付功能"经常"超时，非完全不可用，部分请求仍可成功
- **P1（部分功能炸）**：**命中**。支付核心功能受影响，用户可复现但非 100% 失败
- **P2（边缘问题）**：否。支付是核心链路，非边缘场景

**判定结果**：**P1** — 部分功能受损，需 3 问澄清后直接修

**3 问澄清**：

1. **超时频率和规律**：「经常超时」的具体表现是什么？是高峰期集中超时，还是全天随机超时？平均超时比例大约是多少（如 10 笔中有 1-2 笔）？
2. **超时发生位置**：超时发生在哪个环节？是用户点击支付后等待响应超时（前端等待后端），还是后端调用第三方支付网关超时？错误信息/状态码是什么？
3. **最近变更**：近期是否有支付相关变更（接口升级、第三方 SDK 更新、服务器扩缩容、网络配置变更）？

> 等待用户回答以上 3 个问题后，进入根因分析。

## 步骤 2 · 根因分析准备（Iron Law — 无根因不修复）

**收集症状**（基于已知信息）：
- 症状：支付接口返回超时
- 复现条件：用户支付时，「经常」发生
- 影响：支付核心链路

**需检查**：
- LESSONS.md 历史类似问题 → 无 LESSONS.md（项目无该文件）
- 错误日志、APM 指标、慢查询日志
- 第三方支付网关响应时间监控
- 数据库连接池和网络超时配置

**假设框架**（待澄清后验证）：

| # | 根因假设 | 验证方法 |
|---|---------|---------|
| H1 | 第三方支付网关响应慢/不稳定（最常见） | 检查支付网关 API 响应时间日志，对比超时发生时段的 RT 分布 |
| H2 | 后端超时配置过短（如 HTTP client timeout 设为 3s，但支付网关正常响应需 5-10s） | 检查 HTTP client / 网关调用的 timeout 配置值，对比实际响应时间 |
| H3 | 数据库/连接池瓶颈导致请求排队（高峰期连接池耗尽，支付请求排队等待） | 检查连接池配置、活跃连接数监控、超时时段的 DB 指标 |
