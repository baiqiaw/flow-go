```markdown
# REQUIREMENT — file-upload

## 用户故事
作为 内部管理系统用户，我想 通过拖拽方式上传文件到系统并在列表中预览和删除，以便 在系统内统一管理和分享文件，无需借助外部工具传递。

## 验收准则（BDD）

### AC-1 拖拽上传文件
**Given**: 用户已登录内部管理系统，进入文件管理页面
**When**: 用户将一个或多个文件拖拽到上传区域
**Then**: 文件开始上传，显示上传进度条，上传完成后文件出现在列表中

### AC-2 单文件大小限制
**Given**: 用户选择或拖拽了一个超过 50MB 的文件
**When**: 系统检测文件大小
**Then**: 拒绝上传并提示"文件大小不能超过 50MB"

### AC-3 文件类型安全限制
**Given**: 用户尝试上传一个可执行文件（.exe/.bat/.sh/.cmd/.com）
**When**: 系统检测文件扩展名
**Then**: 拒绝上传并提示"不支持上传可执行文件"

### AC-4 文件列表展示
**Given**: 文件管理页面已加载
**When**: 页面渲染完成
**Then**: 显示所有已上传文件的列表，每项包含文件名、文件大小、上传时间、文件类型图标

### AC-5 文件预览
**Given**: 文件列表中有一张图片或 PDF 文件
**When**: 用户点击该文件的预览按钮
**Then**: 在浏览器内展示文件预览（图片直接显示，PDF 内嵌渲染）

### AC-6 非预览类型文件提示
**Given**: 文件列表中有一个非图片非 PDF 的文件（如 .docx/.zip）
**When**: 用户点击该文件
**Then**: 显示文件名、大小和类型图标，不进行在线预览

### AC-7 删除文件
**Given**: 文件列表中有至少一个已上传文件
**When**: 用户点击某文件的删除按钮并确认删除
**Then**: 该文件从列表中移除，磁盘上的文件同时被删除

### AC-8 同名文件处理
**Given**: 用户上传的文件名与已有文件相同
**When**: 上传完成
**Then**: 新文件自动在文件名后加序号（如 `report(1).pdf`），两个文件共存

### AC-9 上传进度展示
**Given**: 用户正在上传一个大文件
**When**: 上传进行中
**Then**: 显示进度条指示当前上传进度百分比

## 非功能需求
- 性能：单个文件上传 ≤ 50MB 时，上传响应时间取决于网络带宽，不应因服务端处理阻塞超过 5 秒
- 安全：禁止可执行文件上传；文件存储路径不可被外部 URL 直接遍历
- 兼容：支持 Chrome 90+、Firefox 88+、Edge 90+；支持移动端浏览器拖拽区域触摸操作

## Out of Scope（范围排除）
- 不涉及文件版本管理（不支持文件更新/历史版本）
- 不涉及文件权限控制（所有用户可见所有文件）
- 不涉及文件分享/外链功能
- 不涉及批量删除（本次仅支持单文件删除）
- 不涉及文件搜索/筛选功能
- 不涉及云存储集成（仅本地磁盘存储）
- 不涉及断点续传

## Principles（设计约束原则）
- 前端使用 Next.js 现有技术栈，不引入额外 UI 框架
- 后端使用 Express 现有服务，不引入额外文件处理服务
- 文件存储仅使用本地磁盘，不引入对象存储服务
- 上传组件应可复用于未来其他需要文件上传的页面

## Key Decisions（关键决策记录）
| 决策 | 理由 | 影响 |
|------|------|------|
| 不限制文件类型，但禁止可执行文件 | 内部系统用户信任度高，基本限制即可避免安全风险 | 后端需维护黑名单扩展名列表 |
| 图片/PDF 浏览器内预览，其他仅显示图标 | 浏览器原生支持，成本低；其他类型在线预览成本高非必须 | 前端需实现两种预览模式 |
| 文件按日期分子目录存储（YYYY-MM/DD/） | 避免单目录文件过多，方便管理和备份 | 后端存储逻辑需实现日期目录创建 |
| 支持多文件同时上传 | 用户体验好，拖拽场景自然需求 | 前端需处理并发上传队列 |
| 显示上传进度条 | 50MB 大文件用户需要知道进度 | 前端需监听上传进度事件 |
| 同名文件自动加序号共存 | 不同用户可能上传同名文件，覆盖或拒绝都不合理 | 后端需实现文件名冲突检测和重命名逻辑 |

## 术语表
| 术语 | 含义 |
|------|------|
| 拖拽上传 | 用户通过鼠标拖拽文件到浏览器指定区域触发上传的交互方式 |
| 文件预览 | 在浏览器内直接展示文件内容（图片渲染或 PDF 内嵌显示） |
| 文件黑名单 | 禁止上传的文件扩展名列表（如 .exe/.bat/.sh） |
| 本地磁盘存储 | 文件保存在服务器的本地文件系统中（非对象存储或数据库） |
```

```markdown
# CHANGE — file-upload

## Why（为什么做）
内部管理系统当前缺少文件上传和管理能力，用户需通过邮件或 IM 等外部方式传递文件，缺少统一的文件存储和管理入口，降低了协作效率。

## What（做什么）
为内部管理系统新增文件上传功能模块：前端实现拖拽上传组件（支持多文件、进度条、文件列表展示和预览/删除），后端新增文件上传/列表/删除 API，文件按日期目录存储在本地磁盘，支持图片和 PDF 浏览器内预览、同名文件自动加序号、单文件 50MB 上限、可执行文件黑名单拦截。

## 影响面
- 涉及模块：Next.js 前端（上传组件+文件列表页）、Express 后端（文件上传/列表/删除 API）、文件存储层
- 数据库变更：否（文件元信息可暂用内存/JSON 或后续加数据库，本次用本地磁盘 + 简单元信息管理）
- API 变更：是（新增上传、列表、删除三个文件管理 API）
- 依赖变更：是（后端需 multer 等文件上传中间件）
- CONTEXT 需更新：否

## 范围排除（这次不做）
- 文件版本管理
- 文件权限控制
- 文件分享/外链
- 批量删除
- 文件搜索/筛选
- 云存储集成
- 断点续传

## 验收线
文件上传功能可正常使用：拖拽上传成功、列表展示正确、图片/PDF 可预览、可删除文件、50MB 限制和可执行文件拦截生效。

## 路径建议
完整，理由：涉及前后端多模块变更（>5 文件），新增 API 接口，需要设计阶段确定 API 规范和数据流，需要任务拆分保证开发质量。属于新功能开发，建议走完整 8 阶段流程。
```
