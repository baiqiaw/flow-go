# REQUIREMENT — skills-borrow

## 用户故事
作为 flow-go 使用者，我希望流程内置架构决策记录机制，以便 AI 在后续 change 中自动检查已有决策、避免重复建议已否决方案。

作为 flow-go 使用者，我希望流程内置项目词典机制，以便 AI 在需求阶段自动检测术语冲突并维护统一词汇表。

作为 flow-go 使用者，我希望任务拆分时能标记 AFK/HITL 模式，以便并行模式下智能分配任务。

作为 flow-go 使用者，我希望开发阶段有结构化调试流程，以便 AI 不再低效地"加 log 盯着看"。

作为 flow-go 使用者，我希望任务拆分遵循垂直切片原则，以便每个任务可独立验证而非按层堆叠。

作为 flow-go 使用者，我希望设计阶段有深模块原则指导，以便 AI 不会生成大量浅函数。

作为 flow-go 使用者，我希望 HEAVY 级 change 有可选原型子阶段，以便在高不确定性下先验证再实现。

作为 flow-go 使用者，我希望闸门脚本输出格式一致，以便自动化验证不会因格式问题误报。

## 验收准则（BDD）

### AC-1 ADR 机制
**Given**: 一个 change 在设计阶段产出了架构决策
**When**: 该 change 归档后，新的 change 进入设计阶段
**Then**: AI 自动读取 `.specs/adr/` 下所有 ADR，遇到与已否决方案相同的建议时提醒"该方案在 ADR-NNN 中已否决，理由：..."

### AC-2 ADR 创建纪律
**Given**: 设计阶段讨论中产生了一个架构决策
**When**: 该决策同时满足"难以逆转"、"没有上下文会困惑"、"有真实方案取舍"三个条件
**Then**: 自动创建 ADR 文件到 `.specs/adr/NNNN-<slug>.md`，包含背景、选项、决策、理由
**And**: 不满足三个条件的决策不创建 ADR（防止 ADR 流水账）

### AC-3 项目词典自动维护
**Given**: 需求阶段（阶段0）产出了术语表
**When**: 术语写入 `.specs/CONTEXT.md`
**Then**: 后续所有阶段的 AI 行为自动引用 CONTEXT.md 中的术语定义
**And**: 遇到与 CONTEXT.md 冲突的术语时提醒用户

### AC-4 AFK/HITL 任务标记
**Given**: 任务拆分阶段（阶段2）完成
**When**: 查看 TASK.md 中的任务列表
**Then**: 每个任务都有 `mode: AFK | HITL | COLAB` 标记
**And**: 并行模式（parallel）优先分配 AFK 任务给独立 agent

### AC-5 结构化调试流程
**Given**: 开发阶段（阶段3）开发员遇到 bug
**When**: 进入调试子流程
**Then**: 严格按 Phase 1（建反馈闭环）→ Phase 2（复现）→ Phase 3（可证伪假设）→ Phase 4（探测）→ Phase 5（修复+回归测试）→ Phase 6（清理+事后分析）执行
**And**: Phase 1 未建好反馈闭环前不进入 Phase 2

### AC-6 垂直切片任务拆分
**Given**: 任务拆分阶段（阶段2）
**When**: 项目经理将 DESIGN 拆分为任务
**Then**: 每个任务是一个垂直切片（穿透 schema→API→测试），可独立演示
**And**: 任务拆分指南中明确禁止水平切片（按层拆分）

### AC-7 深模块原则
**Given**: 设计阶段（阶段1）进行接口设计
**When**: 技术经理设计模块接口
**Then**: 设计文档包含接口面积评估（方法数、参数复杂度）
**And**: 包含 Seams 纪律检查（两个 Adapter 才是真实 Seam，不要提前抽象）

### AC-8 可选原型子阶段
**Given**: 一个 HEAVY 复杂度的 change 存在设计不确定性
**When**: 进入设计阶段
**Then**: 提示"检测到高设计不确定性，建议进入原型子阶段验证"
**And**: 原型代码明确标注为抛弃型，回答完问题后必须删除或提炼

### AC-9 闸门脚本格式统一
**Given**: 所有闸门脚本（gate_check.py, validate_state.py）
**When**: 运行脚本检查
**Then**: 输出格式完全统一（状态标记一致：✅/❌，缩进一致，字段名一致）
**And**: 脚本内部对工件存在性的检测逻辑与闸门检查表完全对齐

## 非功能需求
- 性能：新增文件和检查不影响现有流程性能（新增开销 ≤ 5%）
- 安全：ADR 和 CONTEXT 文件在归档时被正确处理（不泄露到其他项目）
- 兼容：已归档的 change 不受影响（向后兼容）

## Out of Scope（范围排除）
- Caveman 极简模式（中文语境不适用）
- 独立 Issue 状态机（flow-go 已有闸门体系）
- CONTEXT-MAP.md 多上下文支持（单项目场景）
- 现有归档体系结构改造
- 新的外部依赖引入

## Principles（设计约束原则）
- 所有改动必须与现有 flow-go 风格一致（中文、markdown 工件、脚本用 Python）
- 新增脚本必须与现有 scripts/ 目录风格一致（argparse 入口、JSON 输出、错误处理模式）
- 闸门检查表是工件存在性的唯一真实来源，脚本必须与检查表对齐
- ADR 和 CONTEXT 的格式模板放在 references/artifacts/ 中，与现有模板管理方式一致
- 新增机制在 LITE 复杂度下应有简化路径（不强制要求 ADR 和原型）

## Key Decisions（关键决策记录）
| 决策 | 理由 | 影响 |
|------|------|------|
| ADR 存放在 .specs/adr/ 而非 docs/adr/ | flow-go 以 .specs/ 为中心管理所有规格文件 | 设计阶段需检查该目录 |
| CONTEXT.md 存放在 .specs/ 而非项目根 | flow-go 的项目词典是流程内部概念，不是给最终用户的文档 | 需求阶段需读写该文件 |
| AFK/HITL 标记为 TASK 工件的新增字段而非独立文件 | 最小化改动，复用现有模板结构 | 任务模板需更新 |
| 调试流程嵌入 develop.md 而非独立文件 | 保持阶段文件的完整性，减少文件跳转 | develop.md 篇幅增加 |

## 术语表
| 术语 | 含义 |
|------|------|
| ADR | Architecture Decision Record，架构决策记录。记录重要架构决策的背景、选项、决策和理由 |
| CONTEXT.md | 项目词典文件，记录领域术语定义、避免使用的别名、术语间关系 |
| AFK | Away From Keyboard，可完全交给 AI agent 自动执行的任务 |
| HITL | Human In The Loop，需要人工决策或操作的任务 |
| 垂直切片 | 穿透所有层（schema→API→UI→测试）的薄功能切片，可独立验证 |
| 深模块 | 接口面积小、实现深度大的模块设计原则 |
| Seams 纪律 | 只有两种实现（production + test）时才引入抽象，不为假设的未来替换加接口 |
| 反馈闭环 | 用于调试的快速、确定性、可自动运行的 pass/fail 信号 |
| 抛弃型原型 | 明确标注为临时性的代码，回答完设计问题后删除或提炼 |
