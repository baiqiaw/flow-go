# REQUIREMENT — simplifier-borrow

## 用户故事
作为 flow-go 维护者，我想借鉴 code-simplifier 的设计模式优化 flow-go 的质量闭环机制，以便让 flow-go 从被动流程引擎进化为具备主动质量意识的智能助手。

## 验收准则（BDD）

### AC-1 主动精炼环
**Given**: 开发阶段一个 task 的代码编写完成
**When**: 准备写 SUMMARY.md 之前
**Then**: 自动触发代码精炼检查（检查清单已内嵌在 SKILL.md 的开发阶段描述中），无需用户额外指令

### AC-2 增量闸门检查
**Given**: 同一阶段内已通过一次闸门检查
**When**: 需要再次执行闸门检查（如恢复会话后重入）
**Then**: 只验证自上次检查以来的增量变更，跳过已验证的前置工件

### AC-3 正向首要原则
**Given**: SKILL.md 中的角色红线速查表
**When**: 查看任何角色的约束
**Then**: 每个角色同时拥有"首要原则（必须保护）"和"禁止（绝对不做）"两列

### AC-4 反过度优化护栏
**Given**: LITE 模式的闸门检查或进化系统的 SUGGEST 路径
**When**: 评估是否可以简化/跳过
**Then**: 有明确的"不可简化/不可跳过"症状清单（至少 3 条具体症状）

### AC-5 阶段反模式目录
**Given**: 核心阶段（3-开发、4-测试、5-审查）的执行步骤
**When**: AI 进入该阶段执行任务
**Then**: 阶段描述中包含具体反模式清单（每阶段至少 4 条），用于自我检查

### AC-6 验证闭环
**Given**: 开发 task 完成后或审查修复后
**When**: 准备进入下一阶段
**Then**: 有明确的自我验证子步骤（功能不变 + 质量提升确认），验证结果记录在工件中

## 非功能需求
- 性能：新增检查步骤不增加超过 10% 的 token 消耗（通过复用现有闸门机制实现）
- 安全：所有优化不绕过现有 HARD-GATE 机制
- 兼容：保持与 LITE/STANDARD/HEAVY 三级复杂度的兼容

## Out of Scope（范围排除）
- gate_check.py 脚本修改（增量闸门脚本化留给后续 change）
- 飞轮巡检/进化系统脚本逻辑修改
- model 策略引入
- 0-需求/1-设计/2-任务/6-部署/7-验收阶段核心步骤修改

## Principles（设计约束原则）
- 增量注入而非重构：在现有 SKILL.md 结构上增加内容，不改变 7 步主流程
- 保护 HARD-GATE 完整性：新增优化不得绕过或弱化现有闸门
- 具体 > 抽象：反模式目录必须是具体症状（如"在 task 之外修改文件"），不是抽象原则
- 正向优先：每个"禁止"都配一个"必须保护"，形成正向+负向双重约束

## Key Decisions（关键决策记录）
| 决策 | 理由 | 影响 |
|------|------|------|
| 主动精炼环内嵌在 SKILL.md 而非独立 agent | flow-go 的 Skill 链式调用白名单禁止引入新 skill，内嵌避免白名单冲突 | SKILL.md 开发阶段步骤增加 |
| 增量闸门先以文档描述实现 | 脚本化需要修改 gate_check.py，超出本 change 范围 | 后续 change 可补脚本支持 |
| 反模式目录放在 SKILL.md 角色红线表下方 | 集中管理，不需要额外 reference 文件 | SKILL.md 角色红线速查扩展 |
| 验证闭环不增加新工件类型 | 复用 SUMMARY.md / TEST.md 的现有字段记录验证结果 | 不增加文件管理复杂度 |

## 术语表
| 术语 | 含义 |
|------|------|
| 主动精炼环 | 阶段内自动触发的质量检查子循环，无需用户指令 |
| 增量闸门 | 只验证自上次检查以来变更的前置工件，跳过已验证部分 |
| 正向首要原则 | 角色"必须保护什么"的约束，与"禁止做什么"的红线互补 |
| 反模式目录 | 每个阶段的具体"做了反而更差"症状清单 |
| 验证闭环 | 阶段内"执行→自我验证→确认"的子步骤 |
