**数据流**：
```
task 完成
  → 精炼环（自动触发，无需用户指令）
    → 检查：功能不变？代码更清晰？反模式清零？
    → 不通过 → 修复 → 重入精炼环
    → 通过 → 验证闭环
      → 记录验证结果到 SUMMARY.md
      → 进入下一个 task 或阶段转换
```

## 3. ADR

### ADR 三条件评估

| 决策 | 难以逆转？ | 无上下文会困惑？ | 有真实方案取舍？ | 结论 |
|------|-----------|----------------|----------------|------|
| 精炼环内嵌 SKILL.md vs 独立 agent | 否（可提取） | 是 | 是（独立 vs 内嵌） | 不满足全部 → Key Decision |
| 增量闸门先文档 vs 先脚本 | 否 | 否 | 是 | 不满足全部 → Key Decision |
| 反模式放 SKILL.md vs 放 reference | 否 | 否 | 是 | 不满足全部 → Key Decision |
| 验证闭环复用现有工件 vs 新建工件 | 否 | 否 | 是 | 不满足全部 → Key Decision |

无决策满足 ADR 三条件，全部记入 Key Decisions（已在 REQUIREMENT.md 中记录）。

### Key Decisions（补充设计层决策）

| 决策 | 理由 | 影响 |
|------|------|------|
| 精炼环检查清单内嵌在 SKILL.md 而非引用 reference 文件 | 减少文件加载次数，精炼环是高频操作 | SKILL.md 第六步内容增加约 15 行 |
| 增量闸门通过"已验证工件缓存"实现 | 阶段进度字段已存在于 per-change STATE.md，复用即可 | STATE.md 阶段进度格式需扩展 |
| 反模式目录分阶段列在 SKILL.md 一个表中 | 集中管理便于 AI 一次性加载，避免 3 次文件读取 | SKILL.md 新增约 20 行表格 |
| 验证闭环结果复用 SUMMARY.md 的"自检"字段 | 不新增工件类型，降低文件管理复杂度 | SUMMARY.md 模板需增加验证字段 |

## 4. 风险
| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 精炼环增加 token 消耗 > 10% | 中 | 中 | 精炼环只在 STANDARD/HEAVY 触发，LITE 跳过；检查清单控制在 5 条以内 |
| 正向首要原则与现有红线语义重复 | 低 | 低 | 首要原则聚焦"保护什么"，红线聚焦"禁止什么"，互为补充不重复 |
| 增量闸门文档描述不够精确导致 AI 行为不一致 | 中 | 中 | 关键判断条件用 if-then 格式描述，不留模糊空间 |
| 反模式目录过长导致 SKILL.md 膨胀 | 低 | 低 | 每阶段限制 4-6 条，总计约 20 行 |

## 5. 既有架构对齐
- 触碰模块：SKILL.md（主流程 + 角色红线）、references/stages/3-develop.md、4-test.md、5-review.md

- 沿用决策：LITE/STANDARD/HEAVY 三级分级沿用；Skill 链式调用白名单不变；Token 预算策略不变

## 6. 注入内容规格

### 注入点 A：主动精炼环（AC-1）

注入位置：SKILL.md 第六步·加载执行，Token 预算段落之后

```markdown
### 阶段内精炼环（3-开发阶段，STANDARD/HEAVY）

每个 task 代码编写完成后、写 SUMMARY.md 之前，自动执行精炼环：

1. **功能不变检查**：diff 仅改变实现方式，未改变输入输出行为
2. **反模式清零**：对照阶段反模式速查表，逐条自检
3. **清晰度提升**：至少一处改善（减少嵌套/消除冗余/改善命名/移除不必要的注释）
4. **边界卫生**：改动文件均在 TASK.md write_files 范围内

全项通过 → 写 SUMMARY.md；任一不通过 → 修复后重入精炼环。

LITE 模式跳过精炼环。
```

### 注入点 B：增量闸门（AC-2）

注入位置：SKILL.md 第四步·闸门检查表之后

```markdown
**增量闸门模式**：同一阶段内第二次及后续闸门检查，只验证增量部分：
- 读 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段
- 已在进度中标记完成的工件 → 跳过
- 新增/修改的工件 → 执行完整验证
- 阶段转换（进入新阶段）→ 忽略增量模式，执行完整闸门检查
```

### 注入点 C：正向首要原则（AC-3）

注入位置：SKILL.md 角色红线速查表，替换为双列表格

```markdown
## 角色约束速查

| 角色 | 首要原则（必须保护） | 禁止（绝对不做） |
|---|---|---|
| 产品经理 | 需求忠实于用户意图 | 写实现代码、改技术设计 |
| 技术经理 | 架构一致性 | 设计阶段写实现代码；审查阶段自己改代码 |
| 项目经理 | 需求完整传递到任务 | 改需求内容、改技术设计 |
| 开发员 | 功能对齐 DESIGN.md | 改 REQUIREMENT/DESIGN、跨任务改动 |
| 测试员 | 用例忠实于 REQUIREMENT AC | 自己修代码、删除/弱化失败用例 |
| 运维 | 部署安全性与可回滚性 | 改业务代码、未经审查直接部署 |
```

### 注入点 D：反过度优化护栏（AC-4）

注入位置 A：SKILL.md 第四步·闸门检查，LITE 简化闸门列描述扩展

```markdown
LITE 不可跳过的 3 种场景（即使 LITE 也必须走完整闸门）：
1. 涉及安全相关代码（认证/授权/加密/数据隔离）
2. 改动跨 ≥3 个模块的公共接口
3. 包含数据迁移或数据格式变更
```

注入位置 B：SKILL.md 第七步·状态更新，SUGGEST 路径安全原则之后

```markdown
SUGGEST 不可自动执行的症状清单（出现任一条即需用户逐条确认）：
1. 建议删除现有闸门检查或 HARD-GATE 机制
2. 建议修改角色红线的核心边界
3. 建议增加新的 Skill 链式调用白名单条目
4. 建议绕过 STATE.md 状态管理直接操作文件
```

### 注入点 E：阶段反模式目录（AC-5）

注入位置：SKILL.md 角色约束速查表之后，新增章节

```markdown
## 阶段反模式速查

> AI 进入对应阶段时必须对照此表自检，命中任一条即停止并修正。

### 3-开发 反模式
- 在 TASK.md write_files 范围外修改文件（scope creep）
- 引入 DESIGN.md 未规划的新依赖
- 硬编码本应配置化的值（端口/URL/密钥）
- 跳过错误处理"因为场景太简单不会出错"
- 在 LITE 模式下合并多个 task 的改动到一个 commit

### 4-测试 反模式
- 只测 happy path，跳过边界和异常
- 测试代码与实现代码紧耦合（mock 过深导致测试失去价值）
- 删除或弱化失败的测试用例而非修复实现
- 测试依赖执行顺序（用例间有隐式依赖）

### 5-审查 反模式
- 只审查自己写的代码（违反独立性）
- 审查同时修改代码（违反技术经理红线）
- 跳过跨模块影响分析（"只改了一个文件"）
- 审查报告只有"通过"无具体检查记录
```

### 注入点 F：验证闭环（AC-6）

注入位置：SKILL.md 第六步·加载执行，精炼环段落之后

```markdown
### 阶段内验证闭环

以下场景必须执行验证闭环（自我验证子步骤）：

**开发 task 完成 → 精炼环通过后**：
1. 确认功能不变：grep diff 确认无行为变更（仅实现变更）
2. 确认 verify 通过：重新运行 TASK.md 中的 verify 命令
3. 记录到 SUMMARY.md：在"自检"章节追加「验证闭环：功能不变 ✅ / verify ✅」

**审查修复完成 → 进入下一阶段前**：
1. 确认修复有效：针对每个修复项重新验证
2. 确认无新增问题：修复未引入新的严重项
3. 记录到 REVIEW.md：在评审矩阵后追加「验证闭环：修复有效 ✅ / 无新增严重项 ✅」
```
