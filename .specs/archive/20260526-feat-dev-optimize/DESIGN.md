# DESIGN — feat-dev-optimize

## 0. 技术栈选定
| 候选 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| Markdown prompt 层修改 | 零代码、零依赖、与现有 references/ 风格一致 | 无法做运行时强制 | ✅ |
| Python 脚本层修改 | 可做自动化校验 | 需维护脚本、偏离 feature-dev 的 prompt-only 思路 | ❌ |

最终选择：**Markdown prompt 层修改**。理由：feature-dev 的并行子代理、置信度过滤、多方案对比均为 prompt 引导模式，不需要代码层强制。修改仅涉及 4 个 reference 文件，零依赖。

## 2. 数据流

### AC-1 并行探索数据流
```
1-design.md 步骤 1.5 触发
  → dispatch 2-3 个 explorer 子代理（model: sonnet）
  → 每个子代理独立扫描代码库不同维度
  → 每个子代理返回 5-10 个关键文件路径
  → 主代理读取所有返回的文件
  → 主代理产出综合分析 → 进入步骤 2（技术栈选型）
```

### AC-2 置信度过滤数据流
```
cross-review-matrix.md 子代理 prompt
  → 子代理评审时对每个发现打 0-100 置信度
  → 子代理仅输出 ≥80 的发现
  → 按严重度分组（Critical: ≥90 / Important: 80-89）
  → 主代理收到过滤后的报告 → 修复 → re-dispatch
```

### AC-3 备选方案章节数据流
```
1-design.md 步骤执行 → 到达 DESIGN.md 产出环节
  → spec-artifacts.md DESIGN.md 模板包含「4.5 备选方案」章节
  → 技术经理填写至少 2 个方案对比（LITE 跳过）
  → 交叉评审验证备选方案章节完备性
```

### AC-4 子代理模型选择数据流
```
flow-go 主 skill 第六步 加载执行
  → dispatch 子代理时检查子代理类型
  → explorer / reviewer 类型 → model: sonnet
  → 交叉评审子代理 → model: sonnet（通过 cross-review-matrix.md prompt 模板引导）
  → 主代理决策 → 保持更强模型
  → 子代理失败降级时 → 降级后的主代理自审使用更强模型
```

### AC-5 并行 reviewer 数据流
```
5-review.md 步骤 3 触发
  → dispatch 3 个 reviewer 子代理（model: sonnet）
    reviewer-1: R1 认知过载 + R3 知识重复
    reviewer-2: R2 变更传播 + R4 偶然复杂 + 安全审查
    reviewer-3: R5 依赖混乱 + R6 领域扭曲
  → 每个 reviewer 独立产出问题列表（含置信度）
  → 主代理合并去重 → 进入步骤 5 循环评审
```

本改动不涉及 API。所有修改为 markdown 文件内容变更。

## 4. 备选方案

### 方案 A：全面集成（推荐）
直接在现有 4 个 reference 文件中嵌入并行子代理和置信度过滤逻辑。

| 维度 | 说明 |
|------|------|
| 改动范围 | 4 个文件，每处改动 ≤ 30 行 |
| 风格一致 | 与现有 flow-go reference 风格完全一致 |
| 降级能力 | 子代理失败时主代理可单线程降级 |
| 推荐理由 | 最小改动量、零新增文件、与现有 prompt 引导模式一致 |

### 方案 B：独立配置文件
新建 `references/agent-patterns.md` 集中定义并行子代理规范，各阶段文件引用。

| 维度 | 说明 |
|------|------|
| 改动范围 | 1 新文件 + 4 个文件加引用 |
| 风格一致 | 引入了新的间接层 |
| 降级能力 | 同方案 A |
| 否决理由 | 引入不必要的间接层，4 处改动不需要共享配置 |

**最终选择：方案 A**。理由：改动量小、零新增文件、风格一致。

## 5. ADR

> **ADR 三条件**：创建独立 ADR 文件须同时满足：(1) 难以逆转（改变成本高，回退代价大）、(2) 无上下文会困惑（未来读者会问"为什么这样做"）、(3) 有真实方案取舍（存在明确的替代方案且选择了其中一个）。三条件全满足 → 创建独立 ADR 文件；不满足 → 记录为本节的 Key Decision。

### ADR-001 并行子代理模式嵌入位置
- **背景**：需要决定并行子代理探索逻辑嵌入在哪个阶段
- **选项**：A) 1-设计阶段步骤 1.5 / B) 0-需求阶段步骤 1
- **决策**：A（1-设计阶段步骤 1.5）
- **理由**：feature-dev 在 Phase 2（对应设计阶段）执行探索。0-需求阶段是产品经理角色，不应涉及代码探索。在设计阶段技术栈选型前插入探索步骤，确保选型基于充分的代码库理解。
- **证据级别**：B（feature-dev 已验证此模式有效）

三条件评估：难以逆转 ✅（改变会影响所有使用 flow-go 的项目）/ 无上下文会困惑 ✅ / 有真实方案取舍 ✅

### ADR-002 置信度阈值选择
- **背景**：需要确定评审置信度过滤的阈值
- **选项**：A) ≥75 / B) ≥80 / C) ≥90
- **决策**：B（≥80）
- **理由**：feature-dev code-reviewer 使用 ≥80 阈值，在「高置信度真问题」和「低置信度噪声」之间取得平衡。≥75 会引入过多低价值问题，≥90 可能过滤掉重要的中置信度发现。
- **证据级别**：C（feature-dev 经验值，无本项目量化数据）

三条件评估：难以逆转 ❌（可在 cross-review-matrix.md 中调整）/ 无上下文会困惑 ✅ / 有真实方案取舍 ✅ → **不满足全部条件，记录为 Key Decision 而非独立 ADR 文件**

### ADR-003 并行 reviewer 维度分组
- **背景**：3 个并行 reviewer 如何分配矩阵 C 的 R1-R6 维度
- **选项**：A) 按 feature-dev 的 3 维度分组 / B) 按矩阵 C R1-R6 分组
- **决策**：B（按矩阵 C 分组）
- **理由**：直接复用已有维度体系，避免引入新维度造成评审标准分裂。分组逻辑：R1+R3（认知+重复）、R2+R4+安全（传播+复杂）、R5+R6（依赖+命名）。
- **证据级别**：C（基于评审一致性推断）

三条件评估：难以逆转 ❌ / 无上下文会困惑 ✅ / 有真实方案取舍 ✅ → **不满足全部条件，记录为 Key Decision**

## 6. 风险
| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 并行子代理启动失败或超时 | 中 | 中 | 每个 explorer 步骤标注"如子代理失败，主代理单线程降级" |
| 置信度 ≥80 过滤掉重要问题 | 低 | 高 | 评审 prompt 中引导"宁可多报不可漏报"，≥80 为输出阈值不是内部检测阈值 |
| sonnet 模型探索质量不足 | 低 | 中 | 验证假设表已覆盖此风险（推翻信号：sonnet 遗漏关键文件） |
| 备选方案章节增加设计阶段耗时 | 中 | 低 | LITE 模式跳过；STANDARD/HEAVY 本就需要方案对比 |

## 7. 既有架构对齐
- **触碰模块**：references/stages/1-design.md、references/stages/5-review.md、references/artifacts/spec-artifacts.md、references/cross-review-matrix.md
- **禁动清单**：6 维评审矩阵定义（矩阵 A/B/C 的维度和判定标准不变）、闸门检查通过/失败逻辑、子代理 prompt 基本结构

## 8. 具体改动清单

### 8.1 references/stages/1-design.md
**位置**：步骤 1 和步骤 2 之间（技术栈选型之前）
**操作**：新增步骤 1.5「并行子代理探索」
**衔接方式**：步骤 1（技术栈选型）的输入由步骤 1.5 的综合分析提供

**新增内容骨架**：
```markdown
1.5 **并行子代理探索**（STANDARD/HEAVY 必做，LITE 跳过）：
    dispatch 2-3 个 explorer 子代理（model: sonnet），每个聚焦不同维度：
    - explorer-1："找到与 [需求] 类似的功能，追踪完整实现链路，返回 5-10 个关键文件路径"
    - explorer-2："映射 [需求领域] 的架构层次和抽象，返回 5-10 个关键文件路径"
    - explorer-3（可选）："分析 [需求领域] 的测试模式和扩展点，返回 5-10 个关键文件路径"

    子代理返回后：
    - 合并所有返回的文件列表，去重
    - 主代理逐个读取列表中的文件，建立深度上下文
    - 产出综合分析摘要（模式发现 + 架构洞察 + 关键约束）
    - 将摘要作为步骤 2（技术栈选型）的输入依据

    **降级规则**：子代理启动失败或返回异常 → 主代理自行完成对应维度的探索
    （单线程降级，不中断流程）
```

### 8.2 references/stages/5-review.md
**位置**：步骤 3（代码质量 6 维审查）
**操作**：在现有单线程审查逻辑前增加并行 reviewer 模式
**衔接方式**：并行 reviewer 产出合并后，进入现有步骤 5（循环评审）

**新增/修改内容骨架**：
```markdown
3. **代码质量 6 维审查**：
    dispatch 3 个 reviewer 子代理（model: sonnet），按矩阵 C 维度分组：

    | 子代理 | 覆盖维度 | prompt 聚焦 |
    |--------|---------|-------------|
    | reviewer-1 | R1 认知过载 + R3 知识重复 | 单函数长度、嵌套层级、重复逻辑 |
    | reviewer-2 | R2 变更传播 + R4 偶然复杂 + 安全审查 | 越界改动、过度抽象、密钥泄露 |
    | reviewer-3 | R5 依赖混乱 + R6 领域扭曲 | import 方向、命名一致性 |

    每个 reviewer 输出格式：
    | 问题 | 置信度 | 严重度 | 位置 | 修复建议 |
    |------|-------|--------|------|---------|

    置信度评分标准：0-100，仅报告 ≥80 的问题
    严重度分组：Critical（≥90）/ Important（80-89）

    主代理合并 3 个 reviewer 的输出：
    - 去重：同一位置同一问题取最高置信度
    - 按严重度排序后进入步骤 5（循环评审）

    **降级规则**：子代理失败 → 主代理按矩阵 C 完整 6 维单线程审查
```

**注意**：HEAVY 模式现有的"dispatch 独立子 Agent 二次 cross-review"不受影响（步骤 3 之后执行）。

### 8.4 references/cross-review-matrix.md
**位置**：「子代理调用协议」的 prompt 模板和「子代理约束」两处
**操作**：增强 prompt 模板加入置信度引导

**prompt 模板「约束」部分新增**：
```markdown
## 置信度评分
对每个潜在问题评分 0-100：
- 0-49：低置信度，大概率误报或不重要
- 50-79：中置信度，真实问题但不关键
- 80-89（Important）：高置信度，确认的真实问题
- 90-100（Critical）：极高置信度，必须修复

**仅报告置信度 ≥80 的问题。** 过滤掉低置信度发现以减少噪音。
```

**prompt 模板「输出格式」部分修改**：
```markdown
### 发现问题
- Critical（置信度 ≥90）：
  - {文件:位置 — 问题描述 — 置信度 — 建议修复方向}
- Important（置信度 80-89）：
  - {文件:位置 — 问题描述 — 置信度 — 建议修复方向}
- {全 PASS 则写"无"}
```

**「子代理约束」部分新增**：
```markdown
- 子代理 dispatch 时指定 **model: sonnet**（探索/评审任务不需要最强模型）
- 每个发现必须附带置信度评分（0-100），仅输出 ≥80 的发现
```

**「各阶段调用参数」表格新增列**：
```
| 阶段 | ... | 子代理 model |
|------|-----|-------------|
| 所有阶段 | ... | sonnet |
```
