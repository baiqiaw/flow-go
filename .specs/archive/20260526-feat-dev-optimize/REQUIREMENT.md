# REQUIREMENT — feat-dev-optimize

## 用户故事
作为 flow-go 框架使用者，我想在设计阶段获得更高效的代码探索和多方案架构对比、在审查阶段获得更精准的评审反馈，以便降低 token 成本、减少评审噪音、提高设计决策质量。
当前我无法做到，因为设计阶段依赖主代理单线程探索消耗大量 token、交叉评审无置信度过滤报告所有问题、DESIGN.md 没有备选方案要求，这导致每次设计探索成本高、评审中高价值问题被噪音淹没、设计方案缺少权衡分析。

**当前体验**：用户在设计阶段感到挫败，因为主代理花大量 token 在广度探索上而缺少深度；在审查阶段感到焦虑，因为评审报告充斥低价值问题而真正重要的 bug 可能被忽略。

## 验收准则（BDD）

### AC-1 设计阶段并行子代理探索
**Given**: 用户进入 1-设计阶段，需要探索代码库
**When**: 设计阶段执行代码探索步骤
**Then**: 启动 2-3 个并行 explorer 子代理，每个聚焦不同维度（类似功能/架构层/测试模式），子代理返回 5-10 个关键文件列表，主代理按列表深度阅读建立上下文

### AC-2 交叉评审置信度过滤
**Given**: 交叉评审子代理被 dispatch 执行评审
**When**: 子代理产出评审报告
**Then**: 每个问题附带 0-100 置信度评分，仅报告 ≥80 的高置信度问题，报告按 Critical/Important 分组

### AC-3 DESIGN.md 备选方案章节
**Given**: STANDARD/HEAVY 复杂度的 change 进入设计阶段
**When**: 产出 DESIGN.md
**Then**: DESIGN.md 包含「备选方案」章节，至少列出 2 个方案对比（含各自优缺点和推荐理由），LITE 模式跳过此章节

### AC-4 子代理模型选择
**Given**: flow-go dispatch 子代理执行探索或评审
**When**: 子代理不涉及最终决策（仅探索/评审）
**Then**: 子代理使用 sonnet 模型降低成本，涉及决策的主代理保持更强模型

### AC-5 审查阶段并行 reviewer
**Given**: 5-审查阶段执行代码质量评审（矩阵 C）
**When**: 启动评审子代理
**Then**: 启动 3 个并行 reviewer，按矩阵 C 维度分组：reviewer-1 覆盖 R1 认知过载+R3 知识重复、reviewer-2 覆盖 R2 变更传播+R4 偶然复杂+安全审查、reviewer-3 覆盖 R5 依赖混乱+R6 领域扭曲

## 非功能需求
- 性能：并行子代理启动不增加 >2s 额外延迟
- 兼容：不破坏现有 flow-go 流程（闸门检查、状态管理、角色约束）
- 可维护：新增内容与现有 reference 文件风格一致

## Out of Scope（范围排除）
- 不修改 flow-go 主流程编排脚本
- 不修改 0-需求、2-任务、3-开发、4-测试、6-部署、7-验收阶段
- 不引入外部 MCP Server 或新依赖
- 不修改 flow-go 主 skill 文件的闸门逻辑

## Principles（设计约束原则）
- 所有新增内容与现有 references/ 文件的 markdown 风格一致
- 并行子代理模式为可选增强，子代理失败时主代理可降级为单线程
- 不改变现有闸门检查的通过/失败逻辑
- 置信度过滤是子代理 prompt 层面的引导，不是代码层面的硬限制

## Key Decisions（关键决策记录）
| 决策 | 理由 | 影响 |
|------|------|------|
| 并行探索仅在 1-设计阶段引入 | feature-dev 在 Phase 2 执行探索，与 flow-go 的 1-设计对应 | 需修改 references/stages/1-design.md |
| 置信度阈值设为 ≥80 | feature-dev code-reviewer 使用此阈值，经验证能有效过滤误报 | 需修改 references/cross-review-matrix.md |
| 备选方案仅 STANDARD/HEAVY 要求 | LITE 模式已跳过精炼环，再加备选方案会增加不必要开销 | 需修改 spec-artifacts.md 的 DESIGN.md 模板 |
| 子代理使用 sonnet | feature-dev 的 3 个子代理全部用 sonnet，探索/评审任务不需要最强模型 | 子代理 dispatch 时需指定 model 参数 |
| 并行 reviewer 按矩阵 C 维度分组 | 直接复用已有 R1-R6 维度体系，避免引入新维度造成评审标准分裂 | reviewer-1: R1+R3，reviewer-2: R2+R4+安全，reviewer-3: R5+R6 |

## 术语表
| 术语 | 含义 |
|------|------|
| 并行子代理 | 同时启动多个独立 Agent，各自执行不同任务后汇总结果 |
| 置信度过滤 | 评审子代理对每个发现的问题评分 0-100，只报告 ≥ 阈值的问题 |
| 备选方案 | 设计阶段产出至少 2 个实现方案对比，含各自优缺点和推荐理由 |
