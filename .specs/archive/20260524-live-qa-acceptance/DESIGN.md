# DESIGN — live-qa-acceptance

## 技术选型

本 change 修改的是 flow-go 流程框架的 markdown 文件，不涉及代码级技术选型。关键方案选择：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A: 混合工具策略（首选） | 活体验证步骤通用定义，检测 Playwright/browse 可用性后自动使用，不可用则输出手动指引 | 不引入外部依赖到框架；已有工具时充分利用 | Web 项目验收体验因环境而异 |
| B: 纯手动 | 所有活体验证都输出手动测试指引 | 完全无依赖 | 验收效率低，与 /qa 的自动化理念不符 |
| C: 强制工具 | 要求 Playwright/browse 可用才执行活体验证 | 验收一致性好 | 排除无法运行浏览器的环境 |

**选定方案 A**，理由：符合 REQUIREMENT "不引入新的外部依赖或工具"的约束，同时在实际有工具时不浪费。

排除 B：效率太低，违背引入活体验证的初衷。
排除 C：过度约束，纯库/CLI 项目无需浏览器。

### 项目类型分级检测

```
1LV 启动时自动执行：
├─ 检查项目根目录特征文件
│  ├─ package.json + src/ → Web 应用
│  ├─ go.mod / Cargo.toml / setup.py → CLI/库
│  ├─ README.md 中有 "library" / "sdk" 关键词 → 纯库
│  └─ 无特征文件 → 询问用户
│
├─ 分级执行策略
│  ├─ Web 应用：检测 Playwright/browse 工具可用性
│  │   ├─ 可用 → 自动启动应用 + 浏览器交互测试
│  │   └─ 不可用 → 输出手动测试指引，用户反馈结果
│  ├─ CLI 工具：bash 执行命令行 + 校验输出
│  ├─ 纯库：运行测试套件 + 检查覆盖率输出
│  └─ 无法运行：跳过并记录原因到 UAT.md
│
└─ 环境依赖缺失处理
   ├─ 检测到缺失依赖 → 询问用户「是否安装 {dep}？」
   ├─ 用户确认 → 安装后继续
   └─ 用户拒绝 → 跳过并记录
```

### 角色切换机制

```
产品经理（主角色）
  │
  ├─ 步骤 1LV：产品经理执行活体验证
  │   └─ 发现 Critical/High bug
  │       │
  │       ▼
  │   开发员（临时角色）
  │   · 定位源码
  │   · 最小修复
  │   · 原子提交
  │   · 角色红线：不改无关代码
  │   · 每修复一个 → 回到 bug 位置重验
  │       │
  │       ▼
  产品经理（恢复主角色）
  │
  ├─ 步骤 1RR：产品经理执行验收重验
  └─ 步骤 4+：后续正常流程
```

### 修复循环自调节

```
修复循环每轮结束检查：
├─ Critical/High 合计 ≤ 0 → 退出循环 ✅
├─ 连续 3 轮仍有 Critical/High → 停下报告 ⚠️
├─ 单轮 Critical/High > 5 → 停下报告 ⚠️
│
├─ 停下报告时输出：
│   · 当前 bug 清单（编号/类别/严重度）
│   · 已修复 / 未修复统计
│   · 3 个选项：继续修复 / 回退到 3-开发 / 记录已知问题并继续
│
└─ 单个 bug 修复尝试上限 3 次（超过标记为「阻塞」）
```

## 步骤详细设计

### 步骤 1LV — 活体验证

**触发条件**：步骤 1（UAT 文档验证）已完成
**执行角色**：产品经理

**1LV-1 项目类型检测**
- 扫描项目根目录特征文件（package.json / go.mod / Cargo.toml / setup.py）
- 结合 TASK.md 中 verify 命令和 read_files 判断项目类型
- 判定结果：web / cli / library / unknown
- 结果追加到 UAT.md「活体验证」章节头部

**1LV-2 运行环境准备**
- web：尝试启动 dev server（npm run dev / go run 等），等待端口就绪
  - 启动失败 → 询问用户是否安装依赖或手动启动
  - 用户拒绝 → 跳过活体验证，记录原因，转步骤 4
- cli：无特殊准备
- library：无特殊准备（走测试输出）
- unknown → 询问用户项目类型，按用户回答走对应分支

**1LV-3 核心流程遍历**
- 从 REQUIREMENT.md 用户故事 + AC 提取用户流程
- web 应用：
  - 检测 Playwright/browse 工具可用性
  - 可用 → 逐页/逐路由自动测试，截图留证
  - 不可用 → 输出手动测试指引清单，等用户反馈
- cli 工具：bash 执行关键命令，校验 stdout/stderr/exit code
- 纯库：运行测试套件，收集通过率和输出

**1LV-4 结果记录**
- 逐条写入 UAT.md 活体验证清单（LV-NN）
- 每条格式：| LV-NN | 路径/操作 | 预期结果 | 实际结果 | 状态 | 证据 |
- 状态值：✅ 通过 / ❌ 失败（Critical/High）/ ⚠️ 部分通过（Low/Medium）
- 证据：截图路径 / 命令输出摘要 / 测试输出

**1LV-5 Bug 汇总判定**
- 统计 ❌ 条目，按严重度分类（Critical / High / Medium / Low）
- Critical/High 合计 = 0 → 跳过步骤 1BF/1RR，直接进入步骤 4
- Critical/High 合计 > 0 → 进入步骤 1BF（Bug 修复循环）

### 步骤 1BF — Bug 修复循环

**触发条件**：步骤 1LV 发现 Critical/High 级别 bug
**执行角色**：临时切换为开发员（产品经理暂停）

**1BF-1 角色切换声明**
- 输出「🔧 角色切换：产品经理 → 开发员」
- 明确切换期间的开发员角色红线：最小修复（只改 bug 相关代码）、不改无关代码、不重构不优化、每个修复独立原子提交

**1BF-2 Bug 逐个修复（循环）**
- 按 Critical → High 优先级排序
- 对每个 bug：
  a. 定位源码：从 bug 描述 → TASK.md read_files → grep 搜索定位
  b. 最小修复：仅修改导致 bug 的代码路径
  c. 原子提交：fix(<change-id>): ISSUE-<N> — <简要描述>
  d. 回到 bug 位置重验：在活体验证环境中重新触发该操作
  e. 重验通过 → 标记 bug 状态为「已修复」
  f. 重验未通过 → 重新分析根因，再次修复（同一 bug 最多 3 次尝试）

**1BF-3 自调节检查（每轮结束时执行）**
- 轮定义：所有已知 bug 遍历一轮 = 1 轮
- 检查条件：
  - Critical/High 合计 ≤ 0 → 退出循环
  - 连续 3 轮仍有 Critical/High → 触发停下报告
  - 单轮 Critical/High > 5 → 触发停下报告
  - 单个 bug 修复尝试 ≥ 3 次仍未解决 → 标记为「阻塞」，跳过该 bug

**1BF-4 停下报告（触发自调节阈值时）**
- 输出报告：触发原因、已修复/未修复统计、当前 bug 清单
- 3 个选项：继续修复 / 回退到 3-开发阶段 / 记录已知问题并继续（带病验收）
- 用户选择 1 → 继续修复，重置轮次计数器
- 用户选择 2 → 中断验收，回到 3-开发
- 用户选择 3 → 记录未修复 bug 到 UAT.md，继续

**1BF-5 角色恢复声明**
- 输出「🔧 角色切换：开发员 → 产品经理」
- 进入步骤 1RR（验收重验）

### 步骤 1RR — 验收重验

**触发条件**：步骤 1BF 修复循环完成（或跳过修复直接跳过本步骤）
**执行角色**：产品经理

**1RR-1 全量重走核心流程**
- 重新执行步骤 1LV-3 的核心流程遍历
- 重点关注：修复的 bug 对应路径是否通过、修复是否引入新问题（回归检测）
- 结果追加到 UAT.md「验收重验」章节

**1RR-2 结果判定**
- 原 Critical/High bug 全部通过 → 验收重验通过
- 发现新 Critical/High bug → 判定来源：
  - 新 bug 由修复引入 → 回到步骤 1BF（追加到 bug 清单）
  - 新 bug 非修复引入 → 记录到 UAT.md，询问用户处理方式
- 回到 1BF 的次数上限 = 2 次（超过则停下报告用户决策）

**1RR-3 完成记录**
- UAT.md 追加验收重验总结：重验通过项 / 新发现问题 / 回归次数
- 最终 bug 状态汇总表

2. **步骤数量**：7-acceptance.md 内部步骤从 9 步变为 11 步（新增 1LV/1BF/1RR），这是 7-acceptance.md 文件内部的变化，不影响 SKILL.md 的加载映射表（仍映射到 `stages/7-acceptance.md` + `artifacts/deploy-artifacts.md`）。
3. **SKILL.md 确认无需修改**：已验证 SKILL.md 中无 7-验收入口/完成条件的硬编码文本，全部通过 gate-rules.md 间接引用。

## ADR

### ADR-0001 验收阶段修复循环的角色切换机制

验收阶段的活体验证发现 Critical/High bug 时，由产品经理临时切换到开发员角色进行修复，修复完成后切回。因为产品经理角色红线禁止写代码，但验收阶段发现 bug 后要求立即修复并重验能最快闭环；替代方案是标记 bug 后直接结束验收，但这会导致带病上线，与本次 change 的目标相悖。

文件位置：`.specs/adr/0001-live-qa-role-switch.md`

## Key Decisions

| 决策 | 理由 | 影响 |
|------|------|------|
| 活体验证插入在 UAT 文档验证之后、健康评分之前 | 文档验证确定测什么 → 活体验证实际跑 → 修复可能改代码 → 评分在最终代码上计算 | 7-acceptance.md 步骤重新编号 |
| 自调节阈值：连续 3 轮 / 单轮 > 5 个 Critical/High | 3 轮足够覆盖多数修复场景；>5 个说明问题系统性，不适合继续盲目修 | 阈值可后期调整 |
| Playwright 可用时自动使用，不可用输出手动指引 | 不引入外部依赖到框架，但已有工具时利用 | Web 项目验收体验因环境而异 |
| 同一 bug 修复尝试上限 3 次 | 避免在单个 bug 上无限循环，3 次仍失败说明根因理解不足 | 阻塞 bug 记录到 UAT.md |

## 风险清单

| 编号 | 风险 | 概率 | 影响 | 缓解方案 |
|------|------|------|------|---------|
| R-01 | 修复循环在验收阶段改代码引入回归 | 中 | 高 | 1RR 重验步骤覆盖核心流程；回归超 2 次停下报告 |
| R-02 | 角色切换时产品经理/开发员边界模糊 | 中 | 中 | 1BF 明确角色切换声明和开发员红线（最小修复、不改无关代码） |
| R-03 | 项目类型检测误判 | 低 | 低 | unknown 时询问用户确认；检测仅辅助，不阻塞 |
| R-04 | 活体验证显著延长验收时间（>50%） | 中 | 中 | AC 已约束"不增加超过 50% 验收时间"；web 项目可用 Playwright 自动化加速 |
| R-05 | 环境依赖缺失导致活体验证跳过 | 中 | 中 | 跳过时必须记录原因到 UAT.md；询问用户是否安装 |
| R-06 | 修复循环与 4-测试职责重叠 | 低 | 中 | 文档明确分工：4-测试=技术正确性，7-验收=产品可用性；修复仅针对活体验证发现的用户可感知问题 |
