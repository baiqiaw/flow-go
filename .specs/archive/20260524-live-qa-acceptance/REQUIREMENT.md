# REQUIREMENT — live-qa-acceptance

## 用户故事
作为 flow-go 团队的产品经理，我想在验收阶段实际运行并测试产品，以便在签署验收前发现运行时 BUG，避免带病上线。

## 验收准则（BDD）

### AC-1 活体验证步骤
**Given** 7-验收阶段已进入，应用可启动或已运行
**When** 产品经理执行活体验证步骤
**Then** 系统按用户流程逐页测试，产出活体验证清单（含路径/操作/预期/实际/证据），追加到 UAT.md

### AC-2 不可运行场景处理
**Given** 应用无法启动（纯库/CLI/环境依赖缺失）
**When** 活体验证步骤检测到不可运行
**Then** 按类型分级处理（Web→浏览器/CLI→命令执行/纯库→测试输出），环境依赖缺失时询问用户是否安装，跳过时记录原因到 UAT.md

### AC-3 Bug 修复循环
**Given** 活体验证发现 Critical 或 High 级别 bug
**When** 进入修复循环
**Then** 临时切换到开发员角色，逐个定位源码并最小修复，原子提交（fix(<change-id>): ISSUE-<N> — <desc>），每个修复后回到 bug 所在位置重验，Critical/High 清零后退出

### AC-4 修复循环自调节
**Given** 修复循环正在进行
**When** 连续 3 轮仍有 Critical/High bug，或单轮 Critical/High 合计 > 5 个
**Then** 停下报告用户决策，不继续盲目修复

### AC-5 验收重验
**Given** 修复循环已完成
**When** 执行验收重验步骤
**Then** 重新走活体验证的核心流程，确认修复有效且无新增问题，结果追加到 UAT.md

### AC-6 UAT.md 模板增强
**Given** 新步骤已定义
**When** 产出 UAT.md
**Then** 包含活体验证清单（LV-N）、Bug 清单（编号/类别/严重度/状态/修复提交）、验收重验结果三个新章节

### AC-7 闸门规则更新
**Given** 7-验收阶段新增了活体验证步骤
**When** 闸门检查执行
**Then** 入口条件增加"应用可运行（可选，不阻塞）"提示，完成条件增加"活体验证全通过或已跳过并记录原因"

### AC-8 SKILL.md 更新
**Given** 7-acceptance.md 和 UAT.md 模板已更新
**When** 查看 SKILL.md
**Then** 7-验收的入口条件和完成条件反映新增步骤

## 非功能需求
- 性能：活体验证步骤不增加超过 50% 的验收时间（正常情况下）
- 安全：修复循环中的代码修改遵循 3-开发的角色红线（最小修复，不改无关代码）
- 兼容：与 4-测试阶段不重叠（4-测试=技术验证，7-验收=产品验证）

## Out of Scope（范围排除）
- 不修改 4-测试阶段的任何内容
- 不引入 Playwright/browse 等外部工具依赖
- 不修改 health_scorer.py 的评分逻辑
- 不修改归档/同步/进化反思流程

## Principles（设计约束原则）
- 角色红线优先：修复循环临时切开发员，修复完切回产品经理
- 最小修改：只改 4 个文件，不重构现有步骤
- 分级处理：Web/CLI/纯库/无法运行各有适配方案
- 与 4-测试互补不重叠：技术测试 vs 产品验证

## Key Decisions（关键决策记录）
| 决策 | 理由 | 影响 |
|------|------|------|
| 按项目类型分级处理活体验证 | flow-go 是流程框架，不应强依赖特定运行环境 | 7-acceptance.md 需包含分级逻辑 |
| 修复循环临时切开发员角色 | 产品经理红线"不写代码"，但修复需要写代码 | 需在步骤中明确角色切换点 |
| 活体验证深度统一标准 | 用户选择不做 LITE/STANDARD/HEAVY 区分 | 所有 change 统一验证标准 |
| 环境依赖缺失时询问用户 | 避免跳过可安装的依赖导致漏测 | 交互式决策点 |

## 术语表
| 术语 | 含义 |
|------|------|
| 活体验证 | 实际运行应用并按用户流程测试，区别于文档验证 |
| 文档验证 | 对照 AC 清单逐项打勾，不实际运行应用 |
| 修复循环 | 发现 bug → 修复 → 重验的迭代过程 |
| 验收重验 | 修复循环完成后全量重新走核心流程 |
| 原子提交 | 每个 bug 修复独立一次 git commit |
