# 路径模式定义

> 0-需求阶段步骤 9 产出的路径建议。三种模式的闸门和阶段覆盖差异。

---

## 模式总览

| 模式 | 阶段覆盖 | 适用条件 | 闸门策略 |
|------|---------|---------|---------|
| 完整 | 0→1→2→3→4→5→6→7 | 新功能 / 多文件变更 / 架构影响 | 全量闸门（与 SKILL.md 闸门表一致） |
| 增量 | 0→1→2→3→4→5→7 | 已有 CI/CD 管线的内部工具 / 非生产环境部署 | 跳过 6-部署，其余全量闸门 |
| 最短 | 0→3→4→7 | 单文件改动 / 配置调整 / typo 修复 | 简化闸门（0-需求 → 3-开发 → 4-测试 → 7-验收） |

## 与 HARD-GATE 的关系

HARD-GATE 的核心原则是**不跳过闸门检查本身**——每个经过的阶段都必须通过闸门。路径模式不削弱闸门，而是**减少经过的阶段数量**：

- 完整模式：8 个阶段 × 各自闸门
- 增量模式：跳过 6-部署（不需要部署），因此也不需要 6-部署的闸门。但 5-审查仍需通过（闸门检查 REVIEW.md 严重项 = 0）。7-验收的闸门简化为不需要 DEPLOY.md
- 最短模式：跳过 1-设计/2-任务/5-审查/6-部署。闸门适配：
  - 3-开发闸门：仅需 CHANGE.md（含内联 AC）+ 代码提交。不检查 DESIGN.md / TASK.md
  - 4-测试闸门：仅需代码已提交。不检查 SUMMARY.md
  - 7-验收闸门：仅需 4-测试通过 + CHANGE.md AC 全部满足。不检查 DEPLOY.md / REVIEW.md

**关键区别**：路径模式减少经过的阶段（少做事），而不是降低经过阶段的闸门标准（少检查）。经过的每个阶段仍需完整通过闸门。

## 最短模式的工件简化

最短模式不产出以下工件：DESIGN.md、TASK.md、REVIEW.md、DEPLOY.md。
替代方案：
- CHANGE.md 内含 AC 章节（替代独立 REQUIREMENT.md）
- SUMMARY 简化为 commit message 级别（无需独立文件）
- TEST.md 保留（质量底线不降）
- UAT.md 保留但简化（无健康评分环节）

## 路径选择决策

0-需求阶段步骤 9 输出路径建议时，依据以下判断：

| 信号 | 完整 | 增量 | 最短 |
|------|------|------|------|
| 改动文件预估 > 5 | ✅ | | |
| 涉及架构/API/数据库变更 | ✅ | | |
| 有外部用户/生产环境 | ✅ | ✅ | |
| 有 CI/CD 管线且非生产部署 | | ✅ | |
| 改动文件预估 ≤ 2 | | | ✅ |
| 不涉及架构/API 变更 | | | ✅ |
| 非 bugfix 类型 | ✅ | | |

路径建议由产品经理输出，用户最终确认。用户可覆盖建议（如将最短改为完整），覆盖时记录理由。
