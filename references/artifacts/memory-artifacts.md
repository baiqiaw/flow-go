# 记忆工件模板

> ADR / CONTEXT — 跨 change 持久化的决策与术语记录。

---

## 交叉评审前自检清单

> 在 dispatch 交叉评审子代理之前，逐项检查。全部通过后才调用子代理（节省 token）。

### ADR 自检
- [ ] 标题简洁明确（非占位符）
- [ ] 背景说明了决策上下文（非泛泛描述）
- [ ] 选项表格至少 2 个方案（含现状）
- [ ] 决策与选项表格中某一方案对应
- [ ] 理由回答了"为什么选这个"
- [ ] 状态字段已填写（已采纳 / 已废弃 / 已替代）

### CONTEXT 自检
- [ ] 仅包含领域术语（无通用编程概念）
- [ ] 每条术语一条定义（无实现细节）
- [ ] _避免_ 列表有实际别名（非占位符）
- [ ] Relationships 部分关系准确
- [ ] Flagged ambiguities 记录了已解决的歧义（非"待统一"状态）
- [ ] Example dialogue 存在且能帮助理解术语边界
- [ ] 无 TBD/TODO/待定 占位符
- [ ] 术语与代码命名已交叉验证（无矛盾）

## ADR（.specs/adr/NNNN-\<slug\>.md）

### 三条件前置检查

> 以下三个条件 **全部满足** 时才创建 ADR；否则在 DESIGN.md 的 ADR 段落记录即可。

1. **难以逆转** — 撤回成本高或影响范围广
2. **无上下文会困惑** — 未来团队成员不理解"为什么这样做"
3. **有真实方案取舍** — 至少两个可行方案，各有优劣

一个都不满足 → 不记录；满足 1-2 个 → DESIGN.md 段落记录；全满足 → 正式 ADR。

### 轻量版（覆盖 80% 场景）

> 大多数 ADR 用一段话就能说清楚。只在选项复杂时才用完整版。

```markdown
# ADR-NNNN <标题>

<1-3 句话：什么背景、做了什么决策、为什么。>
```

**示例**：
```markdown
# ADR-0003 使用事件溯源处理订单

写入模型采用事件溯源，读模型投影到 Postgres。因为订单状态变更需要完整审计追踪。
```

### 完整版（重大架构决策使用）

> 当选项 > 2 个、取舍非显然、或后果影响多模块时使用。

```markdown
# ADR-NNNN <标题>

## 背景
<描述触发此决策的问题或需求>

## 选项

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A: <名称> | <简要说明> | <...> | <...> |
| B: <名称> | <简要说明> | <...> | <...> |
| C: <名称> | <简要说明> | <...> | <...> |

## 决策
<选择哪个方案，一句话>

## 理由
<为什么选这个方案，2-3 句>

## 状态
- [ ] 已采纳 / 已废弃 / 已替代（替代为 ADR-XXXX）
```

### 何时用哪个版本

| 条件 | 使用版本 |
|------|---------|
| 3 条件全满足 + 选项显而易见 | 轻量版 |
| 3 条件全满足 + 选项有争议或后果深远 | 完整版 |
| 不满足 3 条件 | DESIGN.md 段落记录，不创建 ADR 文件 |

## CONTEXT.md（.specs/CONTEXT.md）

### 规则

> 以下规则确保 CONTEXT.md 保持精炼、可维护。

- **只记领域术语**，不记通用编程概念（如"回调"、"哈希表"）
- **只记定义**，不记实现细节
- **最小化原则**，能从上下文推断的不记
- **一条一句定义**，避免复合句
- **Inline 更新纪律**：术语在讨论中明确后立即更新，不批量追加。避免跨会话遗忘
- **交叉验证纪律**：用户描述的行为必须与代码实现一致。发现矛盾 → 立即指出并确认以谁为准

### 交叉验证触发点

> 以下场景自动触发术语与代码的交叉验证：

1. **需求阶段**：用户描述"系统支持 X"，grep 代码确认 X 相关接口/模块存在或不存在
2. **设计阶段**：新设计的术语与既有模块命名冲突 → 指出并确认统一
3. **开发阶段**：变量/函数命名与 CONTEXT.md 术语不一致 → 使用规范术语重命名

```markdown
# <项目名> 项目词典

## Language

| 术语 | 定义 | _避免_ |
|------|------|--------|
| <术语A> | <一句话定义> | _避免_ <别名1>、<别名2> |
| <术语B> | <一句话定义> | _避免_ <别名3> |

## Relationships

- <术语A> 是 <术语B> 的 <关系>（如：父/子/同义/反义/依赖）

## Flagged ambiguities

> 标记已发现并解决的歧义术语，防止后人重蹈覆辙。

- <术语X>：曾同时指 <含义A> 和 <含义B> → 已统一为 <含义A>，<含义B> 改称 <术语Y>
- <术语Z>：用户口语中的叫法，已映射为规范术语 <术语A>

## Example dialogue

> 一段简短对话，演示术语在真实讨论中的使用方式。帮助新成员快速理解术语边界。

> **Dev:** "用户发起**借阅**后，**库存**会立即扣减吗？"
> **PM:** "不是立即扣减——**借阅**创建后状态为'待确认'，管理员确认后才扣减**库存**。"
```
