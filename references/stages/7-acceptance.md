# 7-验收（产品经理 + 项目经理）

**角色**：你是产品经理（主）+ 项目经理（辅）。对照需求逐项验收。

**验证心态**：挑战者优先 — 你的首要任务不是"确认功能通过"，而是"找出还没通过的证据"。默认假设功能有问题，只有当证据链充分时才判定通过。宁可多花 10 分钟验证，也不要让一个 bug 溜到生产。

**输入**：全部工件（CHANGE → UAT）

**步骤**：
0. **终止条件扫描**：
   读取 CHANGE.md 的终止条件表，逐条检查：
   - 条件已在某个阶段被触发 → 输出「终止条件 #{N} 已在 {阶段} 被触发」
   - 触发后动作未执行 → 暂停验收，先执行触发后动作
   - 所有终止条件均未触发 → 继续正常验收
1. UAT：对照 REQUIREMENT.md 每条 AC 逐项验证
1AC. **AC 证据链验证**（防误报核心步骤）：对步骤 1 的每条 AC 结论进行证据分级校验
   - **1AC-1 证据分级定义**：
     | 级别 | 证据类型 | 示例 | 可靠度 |
     |------|---------|------|--------|
     | A | 自动化测试通过 | `pytest` / `npm test` 输出含该 AC 对应用例 PASS | 高 |
     | B | 命令行可复现输出 | `curl` 返回预期 JSON / CLI 输出匹配预期 / 数据库查询结果 | 中高 |
     | C | 截图或录屏证据 | 浏览器截图展示正确 UI 状态 / 终端截图 | 中 |
     | D | 主观判断（无硬证据） | "看起来没问题" / "功能正常" | 低 |
   - **1AC-2 分级要求**（按复杂度）：
     - STANDARD/HEAVY：每条 AC 至少 B 级证据。无 B 级证据的 AC 标记为「证据不足」，不可通过
     - LITE：每条 AC 至少 C 级证据。D 级证据不可单独通过，必须升级到 C 级或以上
     - **D 级证据硬约束**：无论何种复杂度，D 级证据（主观判断）永远不可单独判定 AC 通过。发现 D 级 → 必须补充到 C 级或以上
   - **1AC-3 证据链写入**：逐条写入 UAT.md「AC 证据链」清单，格式：| AC-NN | AC 描述 | 证据级别 | 证据内容 | 判定 |。证据内容必须包含具体的命令/文件路径/截图引用，不允许空泛描述
   - **1AC-4 证据不足处理**：
     - 证据级别不满足要求 → 标记该 AC 为「❌ 证据不足」
     - 输出「⚠️ AC-NN 证据不足：当前为 D 级（主观判断），需要 B 级以上证据。建议：<具体获取证据的方式>」
     - 证据不足的 AC > 0 → 回到步骤 1 重新对相关 AC 执行验证，补充符合分级要求的证据后重新进入 1AC 校验
     - 连续 3 次尝试仍无法获取足够证据 → 暂停验收，输出「🛑 AC-NN 无法获取足够证据，可能原因：{分析}。建议：回退到 3-开发 阶段补充自动化测试用例」
1LV. **活体验证**：实际启动应用，按用户流程逐页测试，收集运行时证据
   - **1LV-1 项目类型检测**：扫描项目根目录特征文件（package.json / go.mod / Cargo.toml / setup.py），结合 TASK.md 中 verify 命令和 read_files 判断项目类型。判定结果：web / cli / library / unknown。结果追加到 UAT.md「活体验证」章节头部
   - **1LV-2 运行环境准备**：
     - web：尝试启动 dev server（npm run dev / go run 等），等待端口就绪。启动失败 → 询问用户是否安装依赖或手动启动。用户拒绝 → 跳过活体验证，记录原因到 UAT.md，转步骤 4
     - cli：无特殊准备
     - library：无特殊准备（走测试输出）
     - unknown → 询问用户项目类型，按用户回答走对应分支
   - **1LV-3 核心流程遍历**：从 REQUIREMENT.md 用户故事 + AC 提取用户流程
     - web 应用：检测 Playwright/browse 工具可用性
       - **可用** → 逐页/逐路由自动测试，截图留证。**UI/UX 逐项确认**：每完成一个页面或用户流程的自动测试后，必须向用户展示该页面的测试结果（截图 + 预期 vs 实际对比），逐项询问「页面 {名称}：{操作描述} — 是否通过？」。用户确认通过 → 记录 ✅ 并继续下一页；用户反馈问题 → 记录用户描述的问题到 UAT.md，标记为 ❌，纳入 bug 清单。所有页面必须逐一确认，不可跳过或批量确认
       - **不可用** → 输出手动测试指引清单，逐项等用户反馈确认
     - cli 工具：bash 执行关键命令，校验 stdout/stderr/exit code
     - 纯库：运行测试套件，收集通过率和输出
   - **1LV-3A 对抗性测试**（挑战者优先模式）：核心流程遍历通过后，主动尝试破坏功能
     - **思维切换**：从"确认它能工作"切换为"如果我是一个想让它崩溃的用户，我会怎么操作？"
     - **测试维度清单**（每条 AC 至少覆盖 2 个维度）：
       | 维度 | 具体操作 | 预期行为 |
       |------|---------|---------|
       | 空值/缺失 | 提交空表单 / 删除必填字段 / 传 null 参数 | 友好错误提示，不崩溃 |
       | 非法输入 | 特殊字符 / 超长字符串 / 负数 / SQL 注入 / XSS payload | 输入校验拦截，不产生异常 |
       | 边界值 | 最大值+1 / 最小值-1 / 精度溢出 / 并发竞态 | 边界处理正确 |
       | 权限/状态 | 未登录访问 / 无权限操作 / 重复提交 / 已删除资源访问 | 权限拒绝或状态保护 |
       | 网络/中断 | API 超时 / 断网重连 / 大文件上传中断 | 优雅降级或重试 |
     - **结果记录**：每个维度的测试结果追加到 UAT.md「对抗性测试」清单，格式：| AT-NN | AC 编号 | 测试维度 | 操作描述 | 预期 | 实际 | 状态 |
     - **STANDARD/HEAVY 必须执行对抗性测试**。LITE 模式跳过此步骤（但 1LV-4/1LV-5 仍执行）
   - **1LV-4 结果记录**：逐条写入 UAT.md 活体验证清单（LV-NN），格式：| LV-NN | 路径/操作 | 预期结果 | 实际结果 | 状态 | 证据 |。状态值：✅ 通过 / ❌ 失败。证据：截图路径 / 命令输出摘要 / 测试输出
   - **1LV-5 Bug 汇总判定**：统计 ❌ 条目（含核心流程 + 对抗性测试），按严重度分类（Critical / High / Medium / Low）。所有严重度合计 = 0 → 跳过步骤 1BF/1RR，进入步骤 1IV。任何 bug > 0 → 进入步骤 1BF（Bug 修复循环）
1IV. **独立验证**（防自我偏见）：用独立子代理交叉验证 AC 通过结论
   - **1IV-1 子代理派发**：启动独立子代理（subagent_type=Explore 或 code-reviewer），输入：
     - REQUIREMENT.md 的 AC 清单
     - UAT.md 的「AC 证据链」和「活体验证」章节
     - 关键源文件列表（TASK.md read_files）
     - 验证指令：「以下 AC 被标记为通过。请逐条检查证据链是否充分、是否存在证据与结论不一致的情况、是否有遗漏的失败场景。对每条 AC 给出：通过/质疑/推翻 + 理由」
   - **1IV-2 偏差处理**：
     - 子代理通过率 100%（无质疑/推翻） → 独立验证通过，进入步骤 4
     - 子代理质疑 ≥ 1 条 AC → 暂停，对质疑项重新验证（补充证据或修正结论）。质疑项必须获取 A 级证据才能推翻子代理判断
     - 子代理推翻 ≥ 1 条 AC（发现证据与结论矛盾） → 暂停，对推翻项重新完整验证。推翻项必须进入步骤 1BF 的 bug 清单
   - **1IV-3 验证记录**：子代理结论写入 UAT.md「独立验证」章节：| AC-NN | 主代理判定 | 子代理判定 | 偏差 | 处理结果 |
   - **LITE 模式**：跳过子代理验证（LITE 允许更高信任度），但 1AC 证据链仍必须满足 C 级要求
1BF. **Bug 修复循环**：活体验证发现任何级别 bug 时，临时切换到开发员角色修复
   - **1BF-1 角色切换声明**：输出「🔧 角色切换：产品经理 → 开发员」。明确切换期间的开发员角色红线：最小修复（只改 bug 相关代码）、不改无关代码、不重构不优化、每个修复独立原子提交
   - **1BF-2 Bug 逐个修复（循环）**：按 Critical → High → Medium → Low 优先级排序。对每个 bug：
     a. 定位源码：从 bug 描述 → TASK.md read_files → grep 搜索定位
     b. 最小修复：仅修改导致 bug 的代码路径
     c. 原子提交：fix(<change-id>): ISSUE-<N> — <简要描述>
     d. 回到 bug 位置重验：在活体验证环境中重新触发该操作
     e. 重验通过 → 标记 bug 状态为「已修复」
     f. 重验未通过 → 重新分析根因，再次修复（同一 bug 最多 3 次尝试，超过标记为「阻塞」跳过）
   - **1BF-3 自调节检查（每轮结束时执行）**：轮定义：所有已知 bug 遍历一轮 = 1 轮。检查条件：
     - 所有 bug 已修复（合计 ≤ 0） → 退出循环
     - 连续 3 轮仍有未修复 bug → 触发停下报告
     - 单轮未修复 bug > 5 → 触发停下报告
     - 单个 bug 修复尝试 ≥ 3 次仍未解决 → 标记为「阻塞」，跳过该 bug
   - **1BF-4 停下报告（触发自调节阈值时）**：输出报告：触发原因、已修复/未修复统计、当前 bug 清单。2 个选项：继续修复（重置轮次计数器） / 回退到 3-开发阶段
   - **1BF-5 角色恢复声明**：输出「🔧 角色切换：开发员 → 产品经理」。进入步骤 1RR（验收重验）
1RR. **验收重验**：修复循环完成后全量重走核心流程
   - **1RR-1 全量重走核心流程**：重新执行步骤 1LV-3 + 1LV-3A（含对抗性测试）的核心流程遍历。重点关注：修复的 bug 对应路径是否通过、修复是否引入新问题（回归检测）。结果追加到 UAT.md「验收重验」章节
   - **1RR-2 结果判定**：
     - 原 bug 全部通过 + 对抗性测试全通过 → 验收重验通过
     - 发现新 bug → 判定来源：新 bug 由修复引入 → 回到步骤 1BF（追加到 bug 清单）；新 bug 非修复引入 → 回到步骤 1BF（追加到 bug 清单）
     - 回到 1BF 的次数上限 = 2 次（超过则停下报告用户决策）
   - **1RR-3 完成记录**：UAT.md 追加验收重验总结：重验通过项 / 新发现问题 / 回归次数 / 最终 bug 状态汇总表
   - **1RR-4 独立验证**：重验通过后进入步骤 1IV（独立验证）。子代理输入应额外包含修复前的 bug 清单和修复后的重验结果，以便子代理聚焦验证修复项和回归影响
4. 健康评分：从工件汇总指标，运行 `python3 references/scripts/health_scorer.py`，产出 7 维评分（AC 通过率/测试覆盖/评审效率/代码质量/边界卫生/文档完备/资源效率），评分写入 UAT.md。脚本自动追加到 `health-history.jsonl` 供趋势分析
5. 验收签字：产品经理 + 项目经理分别签字
6. LESSONS 提名：扫 SUMMARY 和 PROGRESS，把符合提名条件的失败经验入库（同时更新 `.lessons.jsonl` 索引）
6A. **疤痕评估**（STANDARD/HEAVY 写入疤痕，LITE 仅评估不写入）：
    检查本 change 是否发生了系统性治理失败（热修/审查 > 2 轮/活体验证 bug > 3/需求返工），如发生则按 `references/scars.md` 写入疤痕到 `.specs/scars/`。未发生则跳过。可选清理 > 90 天的 none-impact 疤痕
7. **进化反思**：
   - **对话反馈分类**（7a，在信号检测前执行）：运行 `python3 references/scripts/feedback_classifier.py --specs-dir .specs/<id> --output .specs/evolution/<id>-classified-feedback.json`，将 `.specs/<id>/user-inputs.jsonl` 中的用户输入分为 project/skill/preference/noise 四类。skill 反馈追加到 `.specs/evolution/skill-feedback.jsonl`。输出分类摘要。LITE 模式使用 `--complexity LITE` 降低灵敏度
   - 运行 `python3 references/scripts/evolution_signal.py --specs-dir .specs/<id>` 从本 Change 工件提取信号
   - 如 `should_reflect=true` → 运行 `python3 references/scripts/evolution_reflect.py --signals <signals.json>` 生成假设
   - 假设输出到 `.specs/evolution/<id>-hypotheses.json`
   - `auto_approve` 中的 low-risk 建议（action_type=add_lesson）直接写入 LESSONS.md
   - 其余建议展示给用户确认
8. 临时文件清理：删除 spec 目录下所有 `*-PROGRESS.md`
9. 走归档流程（同"归档特殊流程"步骤 7-9）
10. **全量同步**：加载 `references/sync-workflow.md` 执行全量同步（非受作用域）。验收 = 归档 + 交接里程碑，全量同步确保知识库与项目状态完全对齐。同步完成后输出变更摘要（记忆 / 文档 / 未处理三层）。此步骤不依赖 SKILL.md 第七步的信号检查，由验收阶段直接触发
11. 走归档流程（同"归档特殊流程"步骤 10-11），将步骤 9-10 的全部变更（含归档文件 + 同步产出的 CLAUDE.md/CONTEXT.md 等）纳入一次 git commit + push + clean 验证

**输出**：`.specs/<id>/UAT.md` + 归档 + 全量同步完成

**入口条件**：DEPLOY.md + 全部工件存在 + 应用可运行（可选，不阻塞，跳过时记录原因）

**完成条件**：AC 证据链全部满足分级要求 + UAT 全通过 + 活体验证全通过或已跳过并记录原因 + 独立验证通过或已跳过（LITE）+ 用户签字 + 全量同步完成 + git 已 push 且 working tree clean

**自检**：
- [ ] AC 逐项覆盖（含证据链分级校验）
- [ ] AC 证据链全部满足分级要求（STANDARD/HEAVY ≥ B 级，LITE ≥ C 级，无 D 级单独通过）
- [ ] 活体验证已执行或已跳过并记录原因
- [ ] 对抗性测试已执行（STANDARD/HEAVY）或已跳过（LITE）
- [ ] 独立验证子代理已执行（STANDARD/HEAVY）或已跳过（LITE）
- [ ] 修复循环角色切换已完成（如适用）
- [ ] 验收重验已通过（如适用）
- [ ] LESSONS 已扫
- [ ] 疤痕评估已执行（步骤 6A 已评估，STANDARD/HEAVY 时已写入或确认无需写入）
- [ ] 进化反思已运行（信号检测 + 假设生成）
- [ ] PROGRESS.md 已清理
- [ ] 归档流程已执行（含 STATE 清理 + 归档索引更新）
- [ ] 全量同步已执行（加载 sync-workflow.md，输出变更摘要）
- [ ] 归档 git commit + push 已完成（含同步产出的文件变更）
- [ ] 终止条件已扫描（CHANGE.md 终止条件表已逐条检查，所有条件均未触发或触发后动作已执行）

**决策信号**：验收完成固定触发全量同步（步骤 10 已内联执行，不依赖 SKILL.md 第七步信号检查）

**中断恢复**：
- 每完成一个步骤后，更新 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段
- 会话恢复时读 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段，从对应步骤继续。UAT.md 中的已完成验收项和活体验证结果仍在
- 阶段完成（UAT 全通过 + 归档）时清空 `阶段进度`
