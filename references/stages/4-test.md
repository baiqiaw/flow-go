# 4-测试（测试员）

**角色**：你是测试员。负责质量验证，不自己修代码，不删除/弱化失败用例。

**输入**：代码 + `.specs/<id>/REQUIREMENT.md` + `DESIGN.md`

**Issue 分类标准**：`references/stages/issue-taxonomy.md`（5 类别 × 4 严重度，Bug 清单每条必须标注）

## 深度分级

测试执行前，根据 TASK.md 的 `depth` 属性（或配置项 `test_depth`）确定测试深度：

| 深度 | 适用场景 | 时间预估 | 行为 |
|------|---------|---------|------|
| **smoke** | 快速验证、热修验证 | ≤5 分钟 | 每轮只验证核心路径，不测边界和异常 |
| **standard** | 默认 | 10-20 分钟 | 5 轮全覆盖，每轮含正常+边界场景 |
| **deep** | 核心模块、安全敏感 | 30 分钟+ | 5 轮全覆盖 + 每轮加异常/压力/回归场景 |

深度与类型适配叠加使用（如 `bugfix + smoke` = 快速验证修复）。

## 步骤

1. **测试就绪检查**（步骤 0，新增）：
   - 检测项目运行时（Go/Node/Python/Rust 等）
   - 检测测试框架是否存在（grep 配置文件和测试目录）
   - 无框架 → 向用户建议安装（不自动安装，保持角色分离）
   - 记录检测结果到 TEST.md 元数据区
2. 从 AC 派生测试矩阵：每条 AC 映射到测试类型和文件
3. 5 轮测试金字塔（按项目类型裁剪）：
   - 第 1 轮 功能：AC 覆盖率，每条 AC 有测试
   - 第 2 轮 性能：响应时间 / 内存 / 并发（量化数据）
   - 第 3 轮 安全：密钥扫描 + OWASP Top 10 快查
   - 第 4 轮 兼容：浏览器 / 平台 / 版本覆盖
   - 第 5 轮 可观测：日志 / 监控 / 告警覆盖
4. 执行测试 + 记录结果（通过/失败 + **证据必填**：截图路径或日志片段）
5. Bug 报告：含类别（issue-taxonomy）+ 严重度 + 复现步骤 + 证据
6. 回归测试：确保旧功能未破
7. **循环评审直到 0 问题**（所有严重度）：

   **Bug 修复纪律**（借鉴 diagnose 方法论 — 反馈循环优先）：

   **铁律（Iron Law）**：未完成根因定位前，禁止提交任何修复代码。违反字面即违反精神。症状修复 ≠ 根因修复——只在出错位置加补丁而不追溯数据源，该 bug 必将在不同入口再次出现。

   每个进入修复循环的 bug 必须遵循以下纪律：

   **Phase 1 — 先建反馈循环**（这是最关键的一步）：
   - 在动手修代码之前，先构造一个能 **确定性地复现该 bug** 的最小信号（不求 100% 复现率，提高复现率即可）
   - 构建优先级（按可行性选择）：
     1. 失败的自动化测试（单元/集成/e2e）
     2. curl/HTTP 脚本对运行中的服务发请求
     3. CLI 调用 + fixture 输入 + 输出 diff
     4. Playwright/Puppeteer 脚本驱动 UI
     5. 回放捕获的 trace/日志/网络请求
     6. 一次性最小 harness
   - 如果 **确实无法构建** 反馈循环 → 停下来向用户说明：列尝试过的方法，请求 (a) 可复现环境访问权 (b) 捕获的 artifact（HAR/日志/core dump） (c) 允许添加临时生产探针。**不要在没有反馈循环的情况下凭猜测修代码**
   - **多组件链路逐层插桩**（当系统涉及多个组件边界时，如 CI→构建→签名 / API→服务→数据库）：
     - 在每个组件边界：记录进入数据 + 记录离开数据 + 验证环境/配置传播
     - 运行一次 → 收集证据 → 定位故障层 → 深入该层
     - 此技术一次运行即可定位故障发生在哪一层，避免逐层猜测

   **Phase 2 — 生成可证伪假设**：
   - 生成 3-5 个假设，按可能性排序
   - 每个假设必须是可证伪的："如果 X 是原因，那么改变 Y 应该让 bug 消失/改变 Z 应该让它更严重"
   - 展示假设列表给用户（用户可能有领域知识瞬间重排序）

   **Phase 3 — 逐个验证**：
   - 每次只改变一个变量
   - 偏好调试器/REPL > 定向日志 > "到处加 log 再 grep"
   - 调试日志必须加唯一前缀（如 `[DEBUG-a4f2]`），修复后一键 grep 清理

   **Phase 4 — 修复 + 回归测试**：
   - 如有合适的测试缝 → 先写失败的回归测试 → 再修代码 → 看测试通过
   - 无合适测试缝 → 记录此发现（代码架构阻止了 bug 被锁定），建议后续架构改进

   **Phase 4.5 — 修复后硬化（Defense-in-Depth）**：
   - 修复 bug 后，追踪坏值数据流：从哪里来，经过哪些层
   - 在数据流经过的每一层添加验证，使 bug 在结构上不可能再发生：
     - Layer 1 入口层：API 边界验证（拒绝明显无效输入）
     - Layer 2 业务层：确保数据对该操作有意义
     - Layer 3 环境守卫：阻止特定上下文下的危险操作
     - Layer 4 调试日志：捕获上下文用于取证
   - 目标：不是"修了一个 bug"，而是"让这个 bug 不可能再发生"
   - 单层验证可被不同代码路径/重构/mock 绕过——多层验证才能结构性防御

   **循环主体**：
   ```
   loop {
     任何 bug > 0:
       1. 构建反馈循环（Phase 1）
       2. 生成假设列表（Phase 2）
       3. 逐个验证（Phase 3）
       4. 修复 + 回归测试（Phase 4）+ 修复后硬化（Phase 4.5）
       5. 用 Phase 1 的反馈循环验证修复
     重测发现 0 个 bug → 退出 loop
     超过 3 轮仍有 bug → 停下报告用户决策
     单个 bug 修复尝试 ≥ 3 次 → 质疑架构（区别于轮次级升级）：
       判定信号：每次修复暴露新的共享状态/耦合/不同位置的问题
       这不是假设失败——这是架构有问题
       停下与用户讨论：继续修补 vs. 重构架构
   }
   ```
   - 每轮确认：(a) 原 bug 已修复（PASS）；(b) 修复未引入新失败（同轮次其他用例仍 PASS）
   - 每轮验证结果追加到 TEST.md Bug 清单的「验证」列
   - 退出条件：所有严重度 = 0（经循环评审确认）
   - 清理：所有 `[DEBUG-...]` 临时日志已删除（grep 确认）

   **红旗自检**（调试过程中闪过以下念头时 → 回到 Phase 1 重新调查）：
   - "先快速修一下，后面再查原因"
   - "多改几处一起试试"
   - "这个应该没问题"
   - "再试一次就好了"（已试过 2+ 次）
   - 修了 A 暴露了 B，修了 B 暴露了 C（→ 触发单 bug 3 次质疑架构）
   - 提出修复方案前未追踪数据流
8. 量化指标：通过率、覆盖率、性能数字
9. **计算测试健康评分**（步骤 N，新增）：
   - 按「测试健康评分规则」计算 5 维加权分数
   - 记录到 TEST.md 健康评分区
   - 如有历史 TEST.md（归档中），对比基线

## 测试健康评分规则

测试阶段产出专属健康评分，独立于项目整体健康评分。

### 5 维度 × 权重

| 维度 | 权重 | 评分规则 |
|------|------|---------|
| 功能覆盖 | 30% | AC 通过率：passed/total × 100 |
| 性能达标 | 20% | 性能指标达标率：达标项/总测项 × 100 |
| 安全合规 | 20% | 安全发现扣分：Critical -40, High -20, Medium -10, Low -5/条（最低 0） |
| 兼容覆盖 | 15% | 目标平台覆盖：已测平台/目标平台 × 100 |
| 可观测完备 | 15% | 可观测覆盖：已覆盖检查点/总检查点 × 100 |

### 计算方式

```
score = Σ(维度分 × 权重)
```

### 分级

| 分数 | 等级 | 含义 |
|------|------|------|
| ≥ 85 | A | 可直接进入审查 |
| ≥ 70 | B | 有改进空间但可接受 |
| ≥ 55 | C | 需要修复后重测 |
| < 55 | D | 质量不达标，建议停下讨论 |

### 基线对比（可选）

如 `.specs/archive/` 中存在同项目的历史 TEST.md：
1. 读取上次评分作为基线
2. 计算各维度 delta
3. 在 TEST.md 中记录对比结果
4. 评分下降 → 醒目标记「⚠️ 较基线下降 N 分」

## 证据强制要求

Bug 清单中**每条 issue 的证据列不可为空**。证据类型：
- **截图**：`screenshots/issue-NNN.png`（UI 类 bug）
- **日志片段**：`关键错误日志（≤10 行）`（后端/运行时 bug）
- **测试输出**：`FAIL: xxx.test.ts:42`（自动化测试失败）
- **性能数据**：`响应时间 8.2s（阈值 3s）`（性能类 bug）

无证据的 issue 视为"未确认"，不进入循环评审。

**自调节机制**（借鉴 gstack WTF-likelihood）：
- **测试轮数上限**：单轮测试修复默认 ≤ 3 轮，超过则报告用户决策
- **失败用例上限**：单轮 bug 合计 > 5 个 → 停下报告，不再逐个修复
- **原子修复**：每个 bug 修复独立提交，格式 `fix(<change-id>): ISSUE-<N> — <desc>`
- **Plateau 停滞告警**（stagnation_patience 控制，默认 3）：
  - 追踪连续轮次中错误数是否减少
  - 连续 stagnation_patience 轮错误数未减少 → 输出告警：
    ```
    ⚠️ 测试 Plateau：连续 {N} 轮修复未减少错误数（当前 {count} 个 bug）
    建议：调整测试策略、扩大 scope、或回退到上一个稳定版本
    ```
  - 不暂停流程（仅建议），由用户决定是否调整
- **结构化迭代日志**（iteration_log 控制，默认 true）：
  - 每轮测试完成后追加一行到 `.specs/<id>/iterations.tsv`
  - 格式：`{timestamp}\t4-测试\t{轮次}\t测试执行\t{status}\t{通过率%}\t{description}`
  - 首次写入时先创建表头行
  - 追加失败时降级告警，不阻塞测试流程

**输出**：`.specs/<id>/TEST.md`

**入口条件**：代码已提交 + SUMMARY.md（含交叉评审 PASS）存在

**完成条件**：5 轮全覆盖或每轮跳过有明确理由 + Bug 清单所有严重度 = 0（**不区分 bug 来源：本次变更、历史遗留、环境差异——发现即属于本阶段，修复到 0 才算完成，不允许以"不是本阶段引起的"跳过任何 bug**） + 测试健康评分已计算

**自检**：
- [ ] 测试从 AC 派生（非从实现派生）
- [ ] 无"看起来没问题"类空话
- [ ] 每轮有量化数据
- [ ] 跳过的轮次有理由
- [ ] Bug 清单中所有严重度项修复后已循环重测（非一次性检查），直到 0 个 bug
- [ ] 铁律遵守：每个修复的 bug 都经过了根因调查（无跳过根因直接修复的情况）
- [ ] 单 bug 修复尝试未超过 3 次未升级（超过 3 次 → 已质疑架构并记录讨论结果）
- [ ] 修复后硬化已执行：每个修复的 bug 都追踪了数据流并在多层添加了验证
- [ ] 红旗自检通过：修复过程中未出现红旗信号（或出现后已回到 Phase 1 重新调查）
- [ ] TEST.md Bug 清单每行有每轮验证结果（可追溯修复历史）
- [ ] 每条 Bug 有证据（截图/日志/测试输出/性能数据）
- [ ] 每条 Bug 有类别标注（功能逻辑/性能/安全/兼容性/可观测）
- [ ] 测试健康评分已计算并记录
- [ ] 深度分级已确认（smoke/standard/deep）

**决策信号**：
- Bug 清单有任何未修复项
- 有跳过轮次（跳过 = 决策）
- 测试健康评分 < 70（C 级以下）

**中断恢复**：
- 每完成一轮测试后，更新 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段：`步骤 N: 第 X 轮完成，通过率 Y%`
- 会话恢复时读 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段，从对应轮次继续。之前轮次的测试数据仍在 TEST.md
- 阶段完成（5 轮全覆盖或每轮跳过有理由）时清空 `阶段进度`

**类型适配**（TASK.md type 属性决定测试重点）：
- bugfix：第 1 轮必须包含复现测试；第 5 轮加强回归测试（验证修复未引入新问题）；可跳过第 2/4 轮
- feature：默认模式，完整 5 轮测试
- refactor：第 1 轮加强行为不变性验证；第 5 轮回归测试权重最高；可跳过第 3 轮（安全测试无新增面）
- doc：跳过第 1-5 轮，改为文档质量检查（链接有效性、代码示例可运行、术语一致性）
- config：第 1 轮加强配置验证（语法/格式/环境差异）；可跳过第 2 轮（性能无变化）；第 5 轮验证配置传播
- chore：第 1 轮验证目标效果达成；可跳过第 2-4 轮；第 5 轮验证无副作用
