# 0-需求（产品经理）

**角色**：你是产品经理。负责需求分析，不写代码，不改技术设计。

**输入**：用户一句话想法 / bug 描述。已有项目时读 README.md + .specs/ 了解背景。

**步骤**：
0. **问题空间回退检查**（前置，先于澄清门控）：
   分析用户输入是**问题描述**还是**解决方案**。
   - 解决方案信号：包含具体功能名（"加个按钮"、"做个导出"、"集成 X"）、技术选型（"用 Redis"、"接 gRPC"）、实现细节
   - 问题描述信号：包含痛点（"每次都要手动复制"、"经常出错"）、场景（"上线前才发现"、"用户抱怨"）、情感（"很烦"、"不敢改"）
   - 检测到解决方案 → 先回退到问题空间：询问"你遇到什么问题，需要加这个？"，获得问题陈述后再进入步骤 1
   - 检测到问题描述 → 直接进入步骤 1

1. **澄清门控**（HARD-GATE — 未通过禁止继续）：

   **阶段 A · 完整性评估**（内部检查，先不输出）：
   逐项评估用户输入在 5 个维度上的信息充分度：
   | 维度 | 充分标准 ✅ | 不充分信号 ❌ |
   |------|------------|--------------|
   | Why（为什么做） | 业务动机明确，有痛点/场景/触发原因 | 缺少痛点或场景描述 |
   | Who（给谁用） | 目标用户角色和权限级别明确 | 只说"用户"但未区分角色 |
   | What（解决什么） | 功能边界清晰，非功能需求有量化指标 | 功能范围模糊，缺少量化约束 |
   | When done（何时算完） | 有明确的时间约束或完成标准 | 无截止日期或"看情况" |
	   | How（感受如何） | 用户情绪和体验痛点明确（挫败、焦虑、困惑等） | 只描述功能缺失，无用户感受 |

   维度状态 = 充分 ✅ / 可推断 ⚠️（有强线索但未明确说）/ 不充分 ❌

   **判断规则**：
   - 5 维全 ✅ → 简要声明各维度充分理由（1-2 句），跳过提问，进入步骤 2
   - 有 ⚠️ 但无 ❌ → 将 ⚠️ 项转为确认式提问（"我理解 X 是 Y，对吗？"）
   - 有 ❌ → 对 ❌ 维度提问，每轮 ≤ 2 问
   - 最多 3 轮提问。第 3 轮仍未澄清的维度，用默认值下走并标明"⚠️ 假设与默认值"让用户事后 review

   **阶段 B · 提问执行**（如需要）：
   - 一条消息只问一个问题，偏好提供选项而非开放式问题
   - 示例：不要问"你想要什么优先级？"，而是问"优先级用哪个框架？"并提供 MoSCoW / ICE / RICE 选项

   **阶段 C · 设计树追问**（阶段 A/B 完成后，STANDARD/HEAVY 级别必做，LITE 跳过）：

   4 维度澄清仅覆盖"Why/Who/What/When done"。需求中隐藏的**设计决策分支**需要逐个遍历确认。此阶段借鉴 grill-me 方法论：不停追问直到双方对每个分支达成共识。

   **执行规则**：
   1. 列出需求涉及的**所有决策分支**（技术选型、交互方式、数据流向、边界条件、异常处理等）
   2. 每个决策分支只问**一个问题**，附带**推荐答案及理由**
   3. 能通过探索代码库回答的问题 → 先探索再问（如"当前用的是什么状态管理？"→ grep 后直接回答）
   4. 用户确认/否定后进入下一个分支，直到所有分支都清晰
   5. 追问结果写入 REQUIREMENT.md 的 Key Decisions 表

   **示例**：
   > "数据存储方式：推荐 SQLite（轻量、零部署、单文件方便备份），理由：本需求是桌面端单用户应用。是否同意？" → 用户确认 → 下一分支

   **禁止**：
   - 禁止一次问多个分支问题（混淆决策点）
   - 禁止不给推荐答案就让用户凭空选择
   - 禁止跳过"能从代码推断"的分支而不先探索代码

   **禁止**（全局）：
   - 禁止以"用户已提供充分信息"为由跳过阶段 A 的逐维度检查。即使信息看起来充分，也必须完成 4 维度表评估
   - 禁止将 ⚠️（可推断）当作 ✅（充分）。⚠️ 必须转为确认式提问
   - 禁止在 ❌ 维度上使用默认值（只在第 3 轮后才允许）
2. **多子系统检测**：分析需求是否涉及多个独立子系统
   - 检测标准：涉及 ≥3 个独立模块 或 影响面 ≥2 个用户角色
   - 检测到 → 建议拆分为多个 change，各自独立走流程。输出：「⚠️ 检测到多子系统需求（N 个模块 / M 个角色），建议拆分：…」
   - 用户确认拆分 → 当前 change 保留最核心子系统，其余排队等待。同时：
     - (a) 创建 `.specs/PIPELINE.md`，写入 N 个 change 行（第 1 个 active，其余 pending），每行包含 7 列（change-id / 描述 / 优先级 / 依赖 / 状态 / 文件范围 / 备注）
     - (b) **文件范围声明**：要求用户为每个 change 声明预期改动的文件 glob 模式（如 `src/auth/**`），填入 PIPELINE.md 的 `文件范围` 列。用于后续并行冲突检测
     - (c) **依赖声明**：询问 change 间依赖关系（哪些 change 需要另一个先完成），填入 PIPELINE.md 的 `依赖` 列
   - 用户拒绝拆分 → 标记为"大型 change"，后续阶段自动启用分段呈现
3. 自动生成 change-id：从描述提取核心关键词，kebab-case（2-4 词），检查 `.specs/<id>/` 不存在
4. 写用户故事 + BDD AC（Given/When/Then），每条 AC 必须可测试
   4.1 **术语表同步到 CONTEXT.md**：
	   - REQUIREMENT.md 术语表章节完成后，同步写入 `.specs/CONTEXT.md`
	   - 使用 `references/artifacts/memory-artifacts.md` 中的 CONTEXT 模板格式
	   - 惰性创建：首次有术语时才创建文件
	   - 写入前读取 `.specs/CONTEXT.md`（如存在），进行术语冲突检测：
	     * 遇到已有术语但定义不同 → 提醒用户确认（"术语 'X' 已有定义 '{旧定义}'，本次描述为 '{新描述}'，是否更新？"）
	     * 遇到已有术语的"避免别名"列表中的词 → 替换为规范术语并提醒
	   - **交叉验证**：对每个新术语，grep 代码库确认命名是否一致。用户说"支持 X"但代码中 X 的实现方式不同 → 立即指出矛盾并确认以谁为准
	   - **Inline 更新**：每个术语确定后立即写入，不批量追加
	   - 更新后重新写入 `.specs/CONTEXT.md`，保留已有术语不变，追加或更新新术语
5. 范围排除：明确"这次不做什么"，至少 1 条
6. 影响面判定：是否改 REQUIREMENT / 涉及架构 / 影响 AC / 需要 CONTEXT 更新。CONTEXT 需更新：是 / 否（如新增术语或有术语定义变更）
7. **<HARD-GATE> 交叉评审前自检**（lightweight）：快速检查 artifact 完整性
   - [ ] 无 TBD/TODO/待定 占位符
   - [ ] AC 条数与用户确认的范围一致
   - [ ] 影响面字段已填写（非空）
   - 自检不通过 → 修复后自检；自检通过 → dispatch 交叉评审子代理
   - **此步骤和步骤 8 是阶段完成的硬性前置条件，不可跳过。未完成禁止转换到 1-设计。**
8. **<HARD-GATE> 交叉评审**（独立子代理，全新上下文）：grep `references/cross-review-matrix.md` 获取矩阵 A（文档评审）定义和子代理 prompt 模板。按模板构造子代理 prompt（传入工件：CHANGE.md + REQUIREMENT.md，上游：用户原始输入 + CONTEXT.md）。子代理输出评审报告到 `<change-id>-REVIEW.md`。任一维度 FAIL → 修文档 → 重新调用子代理重评（无轮数限制，文档不能偏）。6 维全 PASS → 继续。子代理输出异常时按 cross-review-matrix.md 失败处理策略执行。**交叉评审是需求阶段的最后一道质量闸门——未经验证的需求会带着模糊性和遗漏流向设计和开发，越晚发现成本越高。**
9. 路径建议：grep `references/path-modes.md` 获取三种模式定义。根据需求特征（改动文件数、架构影响、部署环境）建议完整/增量/最短路径，附判断理由。用户确认或覆盖路径选择后：
   - (a) 将路径模式写入 CHANGE.md 的 `路径建议` 章节：`完整 / 增量 / 最短，理由：<...>`
   - (b) 将路径模式写入 `.specs/<change-id>/STATE.md` 的 `路径模式` 字段：`完整` / `增量` / `最短`（三选一）
   - (c) 将路径模式写入会话上下文，供后续阶段转换和闸门检查使用

**输出**：`.specs/<id>/CHANGE.md` + `.specs/<id>/REQUIREMENT.md` + `.specs/<id>/<change-id>-REVIEW.md` + `.specs/PIPELINE.md`（如触发拆分）

**入口条件**：无（首个阶段）

**完成条件**：交叉评审报告 6 维全 PASS + 用户确认需求 + AC 后进 1-设计

**自检**：
- [ ] AC 可测试（有 Given/When/Then）
- [ ] 有范围排除（≥ 1 条）
- [ ] 无实现细节（"用 Redux"不该出现在这里）
- [ ] change-id 已声明
- [ ] 交叉评审报告 6 维全 PASS（独立子代理产出）
- [ ] 路径模式已写入 STATE.md（完整/增量/最短，非空）

**决策信号**（满足任一则触发知识库受作用域同步，详见 `references/sync-workflow.md`）：
- 范围排除有实际排除项（非占位符）
- AC 经用户确认（非草稿）
- 影响面判定涉及架构/数据库/API
- 交叉评审经过 2+ 轮才通过

**类型适配**（从用户描述推断类型，影响后续阶段的侧重点）：
- bugfix：澄清门控侧重复现条件（环境/步骤/预期 vs 实际），AC 包含复现步骤和预期行为。范围排除自动排除"顺便改进"
- feature：默认模式，完整的 4 维澄清。AC 侧重用户场景和验收标准
- refactor：澄清门控侧重当前痛点和目标指标（如"启动时间从 5s 降到 2s"），AC 包含可量化的改善目标
- doc：澄清门控侧重受众和场景（给谁看/什么时候看），AC 侧重可读性和可操作性
- config：澄清门控侧重变更影响面（哪些环境/哪些服务受影响），AC 包含回滚条件和环境差异
- chore：澄清门控侧重当前问题和预期效果，AC 简化为"X 问题不再出现"或"Y 指标改善到 Z"

**中断恢复**：
- 每完成一个步骤后，更新 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段：`步骤 N: <一句话简述>`（如 `步骤 5: 范围排除已完成`）
- 会话恢复时读 `.specs/<change-id>/STATE.md` 的 `阶段进度` 字段，从对应步骤继续。之前步骤的产出工件仍在 spec 目录
- 阶段完成（交叉评审 PASS）时清空 `阶段进度`

**对话结构化提取**（用户提供需求讨论记录/会议纪要时）：
1. 识别参与者和角色（谁提需求、谁做技术决策、谁是最终用户）
2. 提取显性需求（直接说出的功能点）
3. 推断隐性需求（参与者未明确说但暗示的约束/偏好）
4. 识别争议点和最终决策（"我说 X / 他说 Y / 最终决定 Z"）
5. 将以上结构化结果写入 REQUIREMENT.md，标记来源（显性/推断）

## 反模式对比表

以下列出需求阶段常见的反模式，帮助区分"问题空间"和"解决方案空间"。

| ❌ 反模式 | ✅ 正确做法 |
|-----------|-----------|
| "用户找不到按钮" | "我是移动端用户，在通勤时想完成支付，但结算按钮在屏幕可视区域下方，导致我放弃购物车、商家损失 42 元平均客单价。感觉很沮丧，因为我准备好买了但 UI 在和我作对。" |
| "需要加个导出功能" | "我是运营经理，想在周会上展示本周数据，但目前只能截图粘贴到 Excel，每次花 30 分钟手工整理，导致我经常拖延周报。感觉很焦虑，因为数据就在系统里但我拿不出来。" |
| "性能太慢了" | "我是数据分析师，想在会议前加载仪表盘，但要 30+ 秒才能渲染完成，导致我无法实时回答问题、显得不专业。感觉很尴尬，因为数据就在那里但我访问不够快。" |
| "系统需要暗色模式" | "我是开发者，经常深夜 review 代码，但明亮界面让眼睛疲劳，导致我频繁休息、失去专注。感觉很不舒服，在最有效率的时间段反而回避使用这个工具。" |
| Why 只写"优化用户体验" | 明确痛点场景、当前障碍和不做后果："用户在 X 场景下被 Y 阻挡，每周浪费 N 小时，不做则 Z" |
| 用户故事只写期望状态 | 同时描述当前痛苦："作为 <角色>，我想 <功能>，以便 <价值>。当前我无法做到，因为 <障碍>，这导致 <后果>" |
