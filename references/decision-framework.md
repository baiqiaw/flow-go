# Decision Framework — 角色协作决策树

> 每个角色遇到边界情况时的升级/回退/求助指引。与角色红线互补：红线说"不能做什么"，Decision Framework 说"遇到困难找谁"。

---

## 产品经理

| 场景 | 动作 |
|------|------|
| 需求涉及技术可行性不确定 | 升级到技术经理，请求可行性评估（非自己判断） |
| 用户需求互相矛盾 | 不自行取舍，列出矛盾 + 影响请用户决策 |
| 需求影响既有系统架构 | 转交技术经理评估影响面（影响面字段标记为"需技术确认"） |
| 多子系统检测后用户拒绝拆分 | 标记为"大型 change"，通知项目经理后续阶段启用分段呈现 |
| AC 无法用 Given/When/Then 表达 | 说明原因，提供替代验收方式（如截图对比/手动测试步骤） |

## 技术经理

| 场景 | 动作 |
|------|------|
| 技术选型存在安全/合规风险 | 升级到用户确认（如选型涉及数据出境/第三方服务） |
| 设计与既有架构严重冲突 | 不强行绕过，列出冲突 + 两个方案（适配 vs 改旧架构）请用户决策 |
| 需求阶段遗漏非功能约束 | 回溯产品经理补齐（非在设计阶段自行假设） |
| 设计评审多轮不通过 | 检查是否需求模糊导致，如是则回溯产品经理澄清 |
| 棕地项目禁动清单与需求冲突 | 列出冲突项，请用户在"改需求"和"改旧代码"间选择 |

## 项目经理

| 场景 | 动作 |
|------|------|
| 任务依赖图有循环 | 回到技术经理重新梳理模块边界，消除循环依赖 |
| 工时预估超出预期 2x+ | 升级到用户，讨论是否缩减范围或拆分阶段 |
| 任务 > 10 个 | 建议用户拆分为多个 change，降低管理复杂度 |
| 优先级排序无法确定 | 请用户参与排序（提供 MoSCoW/ICE 选项） |
| 风险任务占比 > 30% | 升级到用户 + 技术经理，讨论风险缓解或方案调整 |

## 开发员

| 场景 | 动作 |
|------|------|
| TASK 定义有歧义 | 停下反问项目经理澄清（非自行假设实现） |
| 实现需要偏离 DESIGN | 停下，报告技术经理评估偏离影响，获取确认后继续 |
| 发现 DESIGN 有错误 | 不自行修正，报告技术经理更正 DESIGN + 更新评审 |
| 连续编译/运行失败 3 次 | 熔断，报告用户（非继续盲目尝试） |
| 改动涉及 > 5 文件 | 停下确认范围（非自行扩展），可能需拆分任务 |

## 测试员

| 场景 | 动作 |
|------|------|
| Bug 复现不了但用户说有 | 记录为"间歇性"，请用户提供复现步骤/环境信息 |
| Critical/Major 合计 > 5 | 停下报告用户决策（非逐个修到没完） |
| 单轮修复超 3 轮 | 报告用户，可能是根因未对（非继续测） |
| AC 不够明确无法派生测试 | 回溯产品经理澄清 AC（非自行理解） |
| 发现 DESIGN 与实现不一致 | 报告技术经理判断是实现偏离还是设计遗漏 |

## 运维

| 场景 | 动作 |
|------|------|
| 前置 4 问有 ❌ | 不强行部署，走替代路径（本地工具/攒批发布） |
| 健康检查失败 | 不发布，回滚到上一版本 + 通知开发员修复 |
| 环境变量/配置缺失 | 停下，请用户提供正确配置（非自行硬编码） |
| 部署涉及数据库迁移 | 升级到技术经理确认迁移方案安全性 |
| 需要新增 CI/CD pipeline | 不自创，请技术经理确认 pipeline 设计 |

## 优先级模型选择树

> 项目经理在 2-任务阶段排序时使用。当 `priority_framework: auto` 时，按以下决策逻辑自动选择模型。

### 决策逻辑

```
if change_type == "bugfix":
    → MoSCoW（快速分 Must/Should，bugfix 需求明确）

elif resource_constrained and cost_of_delay_quantifiable:
    → WSJF（加权最短作业优先，适合资源受限的敏捷项目）

elif change_type == "feature" and reach_metrics_available:
    → RICE（Reach × Impact × Confidence / Effort，适合面向用户的功能）

elif quick_prioritization_needed or ideation_phase:
    → ICE（Impact + Confidence + Ease，快速粗排）

elif multiple_stakeholder_groups:
    → MoSCoW（多利益方场景，MoSCoW 分类最直观）

elif complex_tradeoffs_across_incommensurable_criteria:
    → Multi-Criteria Decision Analysis (MCDA)

else:
    → MoSCoW（默认兜底）
```

### 模型速查

| 模型 | 适用场景 | 公式 | 输入要求 |
|------|----------|------|----------|
| **MoSCoW** | 通用，多利益方 | Must/Should/Could/Won't | 每条 AC/Task 的优先级标签 |
| **WSJF** | 资源受限 + 敏捷 | (用户价值 + 时间紧迫 + 风险降低) / 作业规模 | 4 项量化评分 |
| **RICE** | 面向用户功能 | (Reach × Impact × Confidence%) / Effort | Reach/Impact/Confidence/Effort |
| **ICE** | 快速粗排/头脑风暴 | (Impact + Confidence + Ease) / 3 | 3 项快速评分 |
| **MCDA** | 多维度不可比标准 | 加权评分矩阵 | 维度 + 权重 + 每项评分 |

### 配置项

`.flowgo-config` 中 `priority_framework` 支持以下值：
- `auto`（推荐）：按决策逻辑自动选择
- `MoSCoW` / `WSJF` / `RICE` / `ICE` / `MCDA`：强制指定
- 默认值：`MoSCoW`

### 使用方式

当 `priority_framework: auto` 时，2-任务阶段的项目经理执行：
1. 读取 CHANGE.md 的 `change_type`（bugfix/feature/refactor/其他）
2. 按决策逻辑选择模型
3. 在 TASK.md 中声明使用的模型及选择理由
4. 按选定模型计算优先级并排序

## 使用方式

阶段执行中遇到上述场景时，grep 本文件对应角色章节，匹配后执行对应动作。未匹配 → 按角色红线执行默认行为（不越权）。

## 跨角色回溯熔断

回溯 = 下游阶段发现问题后，返回上游阶段要求修改。频繁回溯通常意味着早期阶段产出质量不足。

### 回溯计数

每次跨角色回溯时，在 `<change-id>-REVIEW.md` 中记录回溯事件：
```
## 回溯记录
| # | 从阶段 | 到阶段 | 原因 | 时间 |
|---|--------|--------|------|------|
```

### 熔断规则

- **3 次回溯到同一上游阶段** → 停下，输出「⚠️ 回溯熔断：已 3 次回到 {阶段}，建议用户介入评估是否需求/设计有结构性问题」
- **总回溯次数 ≥ 5** → 停下，输出「⚠️ 总回溯熔断：累计 {N} 次回溯，建议暂停流程，用户重新审视需求和设计」
- 熔断后由用户决定：继续（记录决策）/ 回到 0-需求重来 / 废弃

### 级联失效检测

回溯修改上游工件后，下游工件可能基于旧版本。检测规则：
1. 修改 REQUIREMENT.md → 标记 DESIGN.md / TASK.md / SUMMARY.md 为「待验证」
2. 修改 DESIGN.md → 标记 TASK.md / SUMMARY.md 为「待验证」
3. 修改 TASK.md → 标记所有未完成的 SUMMARY.md 为「待验证」

标记方式：在工件顶部增加一行 `> ⚠️ 上游工件已变更，待重新验证`。下游阶段重新进入时，看到此标记必须重新检查本工件与上游的一致性，通过后删除标记。
