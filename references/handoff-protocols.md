# Handoff Protocol — 阶段交接协议

> 每次阶段转换时，上下游角色必须完成上下文转移。闸门检查「工件是否存在」，Handoff 检查「上下文是否传递」。
>
> **数据契约**：每个 Handoff 不仅列确认项，还定义上游必须交付的具体字段。字段缺失 → Handoff 失败 → 停下补齐。

---

## 0→1 需求 → 设计（产品经理 → 技术经理）

**数据契约 — REQUIREMENT.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `business_motivation` | §业务动机 | Why + 用户痛点 |
| `user_roles` | §用户角色 | 角色名 + 使用场景 |
| `acceptance_criteria` | §AC | 每条 AC 含 Given/When/Then + 优先级标签 |
| `non_functional` | §非功能需求 | 性能/安全/兼容性量化指标（非"待定"） |
| `scope_exclusions` | §范围排除 | 排除项 + 排除理由 |
| `review_disputes` | `<id>-REVIEW.md` | 争议点 + 最终决策（如有） |

**FROM 产品经理 传递**：
- 业务动机（Why）和用户痛点摘要
- 用户角色和使用场景
- AC 优先级排序（MoSCoW / ICE）
- 范围排除清单及排除理由
- 隐性需求或非功能约束（性能/安全/兼容）
- 需求评审中的争议点和最终决策

**TO 技术经理 确认**：
- 确认每条 AC 可映射到技术方案
- 确认非功能需求有量化指标（非"待定"）
- 确认范围排除不遗漏技术依赖
- 如有歧义，回溯产品经理澄清（非自行假设）

## 1→2 设计 → 任务（技术经理 → 项目经理）

**数据契约 — DESIGN.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `tech_stack` | §技术选型 | 选定理由 + 备选方案 |
| `architecture_decisions` | §架构决策 | ADR 摘要（决策 + 理由 + 替代方案） |
| `data_flow` | §数据流 | 模块间数据流 + API 契约 |
| `module_dependencies` | §模块依赖 | 模块名 + 依赖方向 + 接口定义 |
| `risk_register` | §风险清单 | 每项风险含 probability/impact/category |
| `integration_constraints` | §既有架构对齐 | 禁动清单 + 沿用决策 |
| `review_disputes` | `<id>-REVIEW.md` | 争议点 + 最终决策（如有） |

**FROM 技术经理 传递**：
- 技术栈选定理由和备选方案
- 架构关键决策（ADR 摘要）
- 数据流和模块依赖关系
- 风险清单及缓解方案
- 既有架构对齐约束（禁动清单 / 沿用决策）
- 设计评审中的争议点和最终决策

**TO 项目经理 确认**：
- 确认架构图足以指导任务拆解
- 确认风险项有对应的任务级处理
- 确认禁动清单在任务中不会违反
- 确认依赖关系可映射到任务 `depends_on`

---

## 2→3 任务 → 开发（项目经理 → 开发员）

**数据契约 — TASK.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `tasks` | §任务列表 | 每个任务含 id/title/description/priority |
| `depends_on` | 每个任务内 | 任务间依赖拓扑（任务 ID 列表） |
| `read_files` | 每个任务内 | 开发前需阅读的文件路径列表 |
| `verify` | 每个任务内 | 可执行的验证命令 |
| `estimated_effort` | 每个任务内 | 预估工时（小时或天） |
| `risk_markers` | 每个任务内 | 风险标记（如适用） |
| `priority_framework` | TASK.md 顶部 | 使用的排序框架及排序结果 |

**FROM 项目经理 传递**：
- 任务优先级和执行顺序
- 并行任务标记和并发约束
- 风险任务标记及注意事项
- 任务间依赖拓扑
- 优先级排序框架及排序结果

**TO 开发员 确认**：
- 确认每个任务的 `read_files` 可访问
- 确认 `verify` 命令可在本地执行
- 确认 `depends_on` 已完成的任务产物可用
- 确认任务粒度在单次 context 内可完成

---

## 3→4 开发 → 测试（开发员 → 测试员）

**数据契约 — SUMMARY.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `files_changed` | §改动文件 | 文件路径 + 变更类型（新增/修改/删除）+ 行数 |
| `verify_output` | §验证结果 | verify 命令真实输出（非"通过"二字） |
| `reused_abstractions` | §沿用抽象 | 沿用的既有类/函数 + grep 结果 |
| `known_issues` | §已知问题 | 未解决问题 + 临时妥协说明 |
| `cross_review_fixes` | §交叉评审 | 修复记录（如有） |
| `scope_check` | §越界检查 | 越界检查通过/未通过 |

**FROM 开发员 传递**：
- 实际改动文件列表和变更说明
- verify 通过的命令输出（真实输出）
- 沿用的既有抽象（grep 结果）
- 已知问题和临时妥协
- 交叉评审中的修复记录

**TO 测试员 确认**：
- 确认 SUMMARY 改动文件表完整
- 确认 verify 输出真实（非"通过"二字）
- 确认越界检查已通过
- 确认已知问题已在测试矩阵中覆盖

---

## 4→5 测试 → 审查（测试员 → 技术经理）

**数据契约 — TEST.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `test_rounds` | §测试轮次 | 每轮结果 + 量化数据（通过/失败/跳过） |
| `bug_list` | §Bug 清单 | 每个 Bug 含 severity + 复现步骤 + 状态 |
| `skipped_rounds` | §跳过轮次 | 轮次 + 跳过理由 |
| `coverage_metrics` | §覆盖率 | AC 覆盖率 + 通过率 |
| `ac_derivation` | §AC 派生追踪 | 每条测试用例关联的 AC ID |

**FROM 测试员 传递**：
- 5 轮测试结果和量化数据
- Bug 清单（含严重度和复现步骤）
- 跳过轮次及理由
- 测试覆盖率和通过率
- 类型适配后的测试重点偏移

**TO 技术经理 确认**：
- 确认 Bug 清单中所有严重度已修复（全部 = 0）
- 确认跳过轮次的理由可接受
- 确认测试从 AC 派生（非从实现派生）
- 确认量化数据可支撑审查结论

---

## 5→6 审查 → 部署（技术经理 → 运维）

**数据契约 — REVIEW.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `spec_compliance` | §Spec 合规 | 合规/不合规 + 具体偏差 |
| `code_quality_6d` | §代码质量 | 6 维审查结果（可读性/安全性/性能/可维护性/一致性/测试覆盖） |
| `security_scan` | §安全审查 | 密钥扫描结果 + OWASP 检查结果 |
| `critical_count` | §问题 | 所有级别问题数量（必须 = 0） |
| `health_score` | §健康评分 | health_scorer.py 输出摘要 |

**FROM 技术经理 传递**：
- Spec 合规审查结论
- 代码质量 6 维审查结果
- 安全审查结论（密钥扫描 + OWASP）
- 所有级别问题修复确认（经循环评审确认 = 0）
- 健康评分结果

**TO 运维 确认**：
- 确认所有级别问题 = 0（经循环评审确认）
- 确认密钥扫描无遗漏
- 确认部署范围与 review 范围一致
- 确认回滚方案可行

---

## 6→7 部署 → 验收（运维 → 产品经理+项目经理）

**数据契约 — DEPLOY.md 必含字段**：
| 字段 | 位置 | 说明 |
|------|------|------|
| `deploy_env` | §部署环境 | 环境 + 部署方式 + 版本号 |
| `health_check` | §健康检查 | 检查项 + 结果（pass/fail） |
| `monitoring` | §监控配置 | 告警规则 + 触发条件 |
| `rollback_plan` | §回滚方案 | 回滚步骤 + 触发条件 |
| `pre_4q` | §前置 4 问 | 4 问结论或替代路径说明 |

**FROM 运维 传递**：
- 部署环境和部署方式
- 健康检查结果
- 监控/告警配置状态
- 回滚方案和触发条件
- 前置 4 问结论（如有替代路径）

**TO 产品经理+项目经理 确认**：
- 确认部署环境与验收环境一致
- 确认 UAT 可在部署环境执行
- 确认监控已就位（验收后不会盲跑）
- 确认回滚方案可执行

---

## Handoff 执行时机

阶段转换时，进入新阶段的角色**必须**执行对应 Handoff 的「TO 确认」项。任一确认项不满足 → 停下，回溯上游角色补齐。

Handoff 检查在闸门检查之后、阶段步骤之前执行。顺序：闸门（工件存在？）→ Handoff（上下文传递？）→ 阶段步骤。
