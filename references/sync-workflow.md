# 知识库同步工作流

> flow-go 内建能力。路由到 `整理/neat/同步` 或决策信号/验收/归档触发时加载此文件执行。

你是一个**知识库编辑**，不是记录员。记录员只会往后追加，编辑会审查全局、合并重复、修正过期、删除废弃。你的工作是让整个项目的知识体系始终保持**干净、准确、对新人友好**的状态。

## 三类知识，三种受众

**三层受众职责不同，不同步任何一层都会出问题——CLAUDE.md 写了不等于 docs 写了，docs 写了不等于记忆更新了。**

| 位置 | 受众 | 职责 | 不同步的代价 |
|------|------|------|--------------|
| **Agent 记忆系统**（若 agent 支持） | Agent 自己跨会话复用 | 个人偏好、非显而易见的项目事实、跨项目 reference | 下次会话 Agent 忘记历史决策 |
| 项目根 `CLAUDE.md` / `AGENTS.md` | 当前项目里的 AI（下次会话自己） | 项目约定、结构、红线、环境变量、路由清单 | 下次 AI 在这个项目里走弯路 |
| 项目 `docs/` + `README.md` | **其他人**（人类同事、下游开发者、未来接手的 AI） | 接入指南、架构图、运维手册、交接说明、API 参考 | **其他人或系统无法正确接入或运维** |

> **Agent 记忆系统的具体位置因平台而异**。完整路径速查见 [agent-paths.md](agent-paths.md)。如果当前 agent 没有独立的记忆系统，直接跳过这一层，把功夫全花在 docs 和项目根 markdown 上。

**平台判定**：看环境变量——`$CLAUDE_CODE` 存在则是 Claude Code，`$CODEX_HOME` 存在则是 Codex，`$OPENCLAW_HOME` 存在则是 OpenClaw，都不存在时默认 Claude Code。

## 三种同步模式

- **全量同步**（手动触发 `整理`）：盘点→识别→修改→自检→摘要，5 步全跑
- **增量同步**（用户说"只同步刚刚改的"）：跳过盘点，处理本次对话变更
- **受作用域同步**（flow-go 自动触发）：只处理本阶段决策信号命中的变更，跳第 1 步，第 2-4 步大幅缩减范围

## 全量同步 / 增量同步 — 第一步：盘点现状

盘点是后续所有判断的基础——漏看一个文件就会漏改，而漏改是这个流程最大的失败。所以先做 ls，再做判断。

1. 列出 agent 的记忆文件（如有）：
   - Claude Code：`ls ~/.claude/projects/<...>/memory/` 并读 `MEMORY.md` 及所有被引用的 `.md`
   - Codex / OpenCode / 其他：找该 agent 的等价位置（见 [agent-paths.md](agent-paths.md)）
2. 对本次对话涉及的**每一个项目**：
   - `ls <project-root>/` → 确认根目录结构
   - `ls <project-root>/docs/ 2>/dev/null` → **枚举所有 docs**（缺失也要确认）
   - `find <project-root> -maxdepth 2 -name "*.md" -not -path "*/node_modules/*" -not -path "*/.git/*"` → 兜底抓散落的 .md
   - 读 `README.md`、`CLAUDE.md` / `AGENTS.md`、每一个 `docs/*.md`
3. 读全局 agent 配置（若有，如 `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）
4. 回顾本次对话全部内容
5. 如果用户没有明确列出变更内容，用 git 提取：
   - `git diff --name-only HEAD~5` 或 `git log --oneline -10` 看最近改了什么
   - `git diff HEAD~1 --stat` 看上一次提交的影响范围
   - 把 git 暴露的文件变更跟对话内容交叉比对，找出所有需要同步的事实变更

**输出一张文件清单**（内部用，不用给用户看），对每个文件标：「评估过 / 要改 / 不用改」。

## 全量同步 / 增量同步 — 第二步：识别变更

**不要只看对话增量有什么新事实，要看新事实会波及哪些文档层级。**

常见模式速览：
- 新增 API / 路由 → CLAUDE.md 路由清单 + integration-guide + architecture 的 Routes
- 新增 / 改名 环境变量 → CLAUDE.md 环境变量表 + runbook + 下游 integration-guide
- 新增数据库表 → CLAUDE.md + architecture 的 Data Model
- 新增大特性（跨多文件） → 以上全部 + architecture 新章节 + handoff 已完成清单
- 跨项目改动 → 上下游两边的 docs **都要对齐**（最常见的漏改场景）
- 记忆层面：相对时间→绝对日期、过期事实→改、重复→合并、已完成待办→删

完整映射表见 [sync-matrix.md](sync-matrix.md)——遇到不确定的改动先查那张表。

**跨项目检查**——这是历次同步最常翻的车。判断方法：
1. 看对话涉及的文件路径——如果出现了两个不同的项目根目录，就是跨项目
2. 看对话里有没有"下游"、"上游"、"调用"、"SDK"、"另一个项目"等关键词
3. 看环境变量——如果一个项目的 `.env` 引用了另一个项目的服务地址，两边都要同步
4. 不确定时，问用户。宁可多问一句，也不要漏改下游文档

## 全量同步 / 增量同步 / 受作用域同步 — 第三步：实际修改

描述改动不算完成——读者看到的是文件内容，不是你的改动描述。必须真的用 Edit/Write/删除工具修改文件。

**顺序建议**：先改 docs/（对外部读者影响最大）→ 再改 CLAUDE.md/AGENTS.md → 最后理记忆。先动外部优先级最高的，即使中途被打断，读者看到的也是对齐的最新状态。

**编辑原则**：

- **合并优于追加**：新信息是对旧信息的更新，改旧条目，不要再加一条
- **删除优于保留**：完成的临时计划、推翻的决策、过期的上下文，删掉
- **精确优于冗长**：一条记忆说清楚一件事，别塞三件
- **绝对时间**：永远写 `2026-04-29`，不写"今天"、"最近"——三个月后"今天"是哪天就没人知道了
- **面向读者**：docs/ 的读者是"第一次接触这个项目的外部人"，写的时候想象对方只有 5 分钟能看完
- **受众不混**：CLAUDE.md 里不抄 docs/ 的全文，docs/ 里不写"我记得上次……"——这是记忆的事

**全局配置极度克制**：`~/.claude/CLAUDE.md` / `~/.codex/AGENTS.md` 只有用户在对话中明确表达了**跨项目的核心原则**才动。日常项目细节绝不进全局。

**docs/ 编辑要点**——新增一个能力的文档变更通常要四处都补：
1. **integration-guide** 或对应"外部视角"文档：加**怎么用**（curl / SDK 示例 / 错误码表）
2. **architecture**：加**怎么工作**（数据流、状态机、设计取舍）
3. **runbook**：加**怎么运维**（冒烟命令、故障排查、环境变量）
4. **handoff** 或 CHANGELOG：加**已完成**

API 速查表、环境变量表、术语表是高频查询的结构化信息，**必须保持"所见即最新"**。

## 受作用域同步 — 专用流程

flow-go 第六步决策同步检查触发时，执行受作用域同步——比增量同步更轻量，只同步当前阶段产出的决策到对应文档层：

1. 跳过第一步完整盘点，只读当前阶段的产出工件（.specs/<id>/ 下本阶段新增/变更的文件）
2. 只处理决策信号命中的变更（不是"本次对话所有变更"）
3. 同步范围限制为：
   - 决策内容写入 CONTEXT.md「已锁决策」表（如存在）
   - 如决策涉及架构/API/数据库变更，同步到 CLAUDE.md / AGENTS.md 对应章节
   - 如 docs/ 已存在且决策涉及外部接口，同步到 docs/ 对应章节
   - 不动记忆层（阶段级决策不改变跨会话偏好）
4. 过自检清单，但只检查受作用域内的条目
5. 输出单行摘要：`🔄 同步完成：CLAUDE.md 更新 X 处，CONTEXT.md 更新 Y 处`

## 全量同步 / 增量同步 / 受作用域同步 — 第四步：自检清单

改完后逐条检查：

- [ ] 第一步列出的每个文件，都判断了"不用改"或"已改"
- [ ] 记忆索引（若有）里的每个链接指向存在的文件
- [ ] 每个记忆文件的 description 和内容对得上
- [ ] 记忆之间没有互相矛盾
- [ ] CLAUDE.md / AGENTS.md 里提到的路径 / 命令 / 工具 / 环境变量在代码中真实存在
- [ ] README 的安装 / 运行步骤跟代码一致
- [ ] 新增 API 路由：**在 integration-guide 和 architecture 都出现了**
- [ ] 新增环境变量：**在 runbook 和项目根 markdown 都出现了**
- [ ] 新增数据库表：**在 architecture 的 Data Model 和项目根 markdown 都出现了**
- [ ] 跨项目影响：下游项目的 docs 也跟着改了
- [ ] 没有相对时间遗留（`grep -E "今天|昨天|刚刚|最近|上周|today|yesterday|recently"` 清零）
- [ ] `.env.example`（如有）与 CLAUDE.md / runbook 的环境变量表一致——新增变量要加，废弃变量要标注
- [ ] `CHANGELOG`（如有）记录了本次变更摘要
- [ ] 重命名 / 删除的符号（表名、字段名、函数名、环境变量）已用 grep 确认无残余旧引用

哪条打不了勾，**回去补**。自检是这个流程的灵魂——跳过它就等于放弃质量保证。

## 全量同步 / 增量同步 / 受作用域同步 — 第五步：变更摘要

在所有文件修改完之后（不是之前），给用户简洁摘要：

```
## 同步完成

### 记忆变更
- 更新：xxx（原因）
- 新增：xxx
- 删除：xxx（原因）

### 文档变更（按项目分组，每个项目列全改动的文件）
- <项目 A>/CLAUDE.md — xxx
- <项目 A>/docs/integration-guide.md — xxx

### 未处理
- xxx（为什么没处理，比如需要用户确认）
```

只列有实际变更的条目。没改的不写。

## 特殊情况

**项目还没有 README 或 CLAUDE.md/AGENTS.md**：判断项目是不是到了"有可运行代码"的阶段。是 → 创建。还在 vibe 阶段 → 跳过，但在摘要里提一句。

**项目没有 docs/ 目录或 docs/ 结构不符合约定**：先确认项目处于什么阶段：
- 有可运行代码 + 有用户 / collaborators → 创建标准 docs/ 结构（integration-guide、architecture、runbook、handoff），用对话中已有的信息填充
- 有可运行代码但还很早期 → 至少确保 README.md 和项目根 markdown 跟代码一致，docs/ 等项目稳定后再建
- 发现 docs/ 但文件名不标准 → 按现有文件名同步内容，不重命名别人的文件，但在摘要里建议标准化

有用户/下游的项目，docs/ 缺失比 docs/ 过期更严重——过期能慢慢修，缺失意味着接手者完全找不到信息。

**对话没有产生新事实**：审查现有记忆和文档有没有过期 / 冲突 / 相对时间——审查本身就有价值。

**记忆之间出现无法自动判断的矛盾**：列在「未处理」让用户决定。

**跨项目改动**：每个项目都要跑一次完整的第一步（ls + 读 docs）。不要假设一个项目的 docs 改了，另一个就不用。

**发现之前的同步漏了东西**：修掉。过去漏洞也归你管。

**增量同步**：如果用户明确说"只同步刚刚改的"或"增量同步"，跳过第一步的完整盘点，只处理本次对话涉及的变更。但仍然要过自检清单——增量同步漏改的概率更高，自检的兜底作用更大。如果不确定是否该增量，默认全量。
