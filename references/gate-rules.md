# Gate Rules — 闸门检查与角色约束

> 从 SKILL.md 外置的规则文件。按分类标签组织，支持 `--categories` 按需加载。
> 分类：gate（闸门前置）/ role（角色约束）/ safety（安全场景）

---

## 1. 闸门检查规则 [gate]

### 1.1 完整路径闸门（默认）

| 进入阶段 | 必须存在（STANDARD/HEAVY） | LITE 简化闸门 | 缺失时 |
|---|---|---|---|
| 0-需求 | 无 | 同 STANDARD | 直接进 |
| 1-设计 | CHANGE.md + REQUIREMENT.md + `<change-id>-REVIEW.md`（需求评审 PASS） | LITE 跳过此阶段 | 提示先跑 0-需求 |
| 2-任务 | REQUIREMENT.md + DESIGN.md + `<change-id>-REVIEW.md`（设计评审 PASS） | LITE 跳过此阶段 | 提示先跑 1-设计 |
| 3-开发 | DESIGN.md + TASK.md（含 verify）+ `<change-id>-REVIEW.md`（任务评审 PASS）；指定任务时验证该任务存在且 depends_on 已完成 | CHANGE.md（含内联 AC） | 提示先跑 2-任务 |
| 4-测试 | 代码已提交 + SUMMARY.md（含交叉评审 PASS + 无已知问题） + **TEST.md Bug 清单所有严重度 = 0（不区分 bug 来源：本次变更/历史遗留/环境差异，发现即修复，不允许"不是本阶段引起的"跳过）** | 代码已提交 | 提示先跑 3-开发 |
| 5-审查 | TEST.md + 全部 SUMMARY | LITE 跳过此阶段 | 提示先跑 4-测试 |
| 6-部署 | REVIEW.md（所有级别问题经循环评审确认 = 0） | LITE 跳过此阶段 | 提示先跑 5-审查 |
| 7-验收 | DEPLOY.md + 全部工件 + 应用可运行（可选，不阻塞，跳过时记录原因） | 4-测试通过 + CHANGE.md AC 全部满足 + 活体验证全通过或已跳过并记录原因 | 提示先跑 6-部署 |

### 1.2 最短路径闸门（0→3→4→7）

跳过阶段 1-设计 / 2-任务 / 5-审查 / 6-部署。跳过的阶段不进入、不检查闸门。

| 进入阶段 | 必须存在（STANDARD/HEAVY） | LITE 简化闸门 | 说明 |
|---|---|---|---|
| 0-需求 | 无 | 同 STANDARD | 与完整路径相同 |
| 3-开发 | CHANGE.md（含内联 AC）+ 代码提交 | CHANGE.md（含内联 AC）+ 代码提交 | 不检查 DESIGN.md / TASK.md。AC 内联在 CHANGE.md 中 |
| 4-测试 | 代码已提交 + **Bug 清单清零（不区分来源）** | 代码已提交 + **Bug 清单清零（不区分来源）** | 不检查 SUMMARY.md，但 Bug 清零是所有路径的硬性要求 |
| 7-验收 | 4-测试通过 + CHANGE.md AC 全部满足 + 应用可运行（可选） | 4-测试通过 + CHANGE.md AC 全部满足 + 应用可运行（可选） | 活体验证全通过或已跳过并记录原因；不检查 DEPLOY.md / REVIEW.md |

### 1.3 增量路径闸门（0→1→2→3→4→5→7）

跳过阶段 6-部署。

| 进入阶段 | 必须存在（STANDARD/HEAVY） | LITE 简化闸门 | 缺失时 |
|---|---|---|---|
| 0-需求 | 无 | 同 STANDARD | 直接进 |
| 1-设计 | 同完整路径 | LITE 跳过此阶段 | 提示先跑 0-需求 |
| 2-任务 | 同完整路径 | LITE 跳过此阶段 | 提示先跑 1-设计 |
| 3-开发 | 同完整路径 | CHANGE.md（含内联 AC） | 提示先跑 2-任务 |
| 4-测试 | 同完整路径 | 代码已提交 + **Bug 清单清零（不区分来源）** | 提示先跑 3-开发 |
| 5-审查 | 同完整路径 | LITE 跳过此阶段 | 提示先跑 4-测试 |
| 7-验收 | 全部工件（不需要 DEPLOY.md）+ 应用可运行（可选） | 4-测试通过 + CHANGE.md AC 全部满足 + 活体验证全通过或已跳过并记录原因 | 提示先跑 5-审查 |

**闸门脚本化验证**：`python3 references/scripts/gate_check.py --stage <N> --change-id <id> --specs-dir .specs/<id> --complexity <level> --path-mode <full|incremental|shortest> [--categories gate]`

### 1.4 证据闸门 [evidence]

适用：STANDARD/HEAVY 复杂度 + 完整/增量路径。LITE + 最短路径跳过。
定义详见 `references/evidence-tiers.md`。

| 检查项 | 条件 | 缺失时 |
|--------|------|--------|
| 技术选型证据 | 每个首选方案有 >=B 级证据或附 C 级+验证计划 | 提示补强证据 |
| ADR 证据 | 每个 ADR 的"决策"字段标注证据级别 | 提示补标注 |
| D 级决策 | 无架构关键决策仅依赖 D 级证据 | FAIL，必须验证或换方案 |

插入时机：1-设计阶段步骤 8（自检）中新增一项"证据分级已标注"

### 1.5 假设闸门 [hypothesis]

适用：STANDARD/HEAVY 复杂度（所有路径）。LITE 跳过。

| 检查项 | 条件 | 缺失时 |
|--------|------|--------|
| 验证假设 | CHANGE.md 验证假设表 >=1 条 | 提示补充 |
| 推翻信号 | 每条假设有明确的可观测信号 | 提示补充 |
| 终止条件 | CHANGE.md 终止条件表 >=1 条 | 提示补充 |
| 触发后动作 | 每条终止条件有回退/重评估/废弃选项 | 提示补充 |

插入时机：0-需求阶段步骤 7（自检）中新增一项"验证假设和终止条件已填写"

### 1.6 意图闸门 [intent]

适用：STANDARD/HEAVY 复杂度（所有路径）。LITE 跳过。

| 检查项 | 条件 | 缺失时 |
|--------|------|--------|
| 意图验证完成 | 阶段 D 5 个检查项全部通过或用户已确认承担风险 | 提示先完成意图验证 |

插入时机：0-需求阶段步骤 7（自检）中新增一项"意图验证已完成（5 项全通过或用户确认）"

### 1.7 质量维度 [quality]（信息性，不阻塞）

> 借鉴 Kim_Decision 的闸门深度设计。现有闸门检查产物存在性，本节增加内容质量维度的 AI 自检提示。不阻塞闸门通过，仅在自检步骤中输出质量警告供参考。

适用：STANDARD/HEAVY 复杂度。LITE 跳过。

| 阶段闸门 | 质量检查项 | 警告条件 |
|----------|-----------|---------|
| 0-需求 | AC 含量化成功标准 | > 50% 的 AC 缺少量化指标 |
| 0-需求 | AC 含 Given/When/Then 结构 | 有 AC 缺少 BDD 结构 |
| 1-设计 | 关键决策有 >=B 级证据 | > 50% 的关键决策仅 C/D 级证据 |
| 4-测试 | 测试矩阵覆盖边界场景 | 仅覆盖 happy path |
| 7-验收 | AC 证据链满足分级要求 | 有 AC 仅有 D 级（主观判断）证据就标记通过 |
| 7-验收 | 对抗性测试覆盖 ≥2 维度/AC | 仅验证 happy path 就签字 |

执行方式：在各阶段自检步骤中追加一项"质量维度检查"。不通过时输出「⚠️ 质量警告：<检查项>：<具体问题>」，但**不阻塞闸门通过**。由 AI 主观判断而非脚本硬判。

### 1.8 7-验收 完成闸门 [completion]

> AC 证据链和独立验证是 7-验收阶段内部步骤的产出，属于「完成闸门」（阶段转换前检查），不是「进入闸门」（前置条件检查）。

适用：所有路径模式。按复杂度区分检查严格度。

| 检查项 | STANDARD/HEAVY | LITE | 缺失时 |
|--------|---------------|------|--------|
| AC 证据链 | 每条 AC ≥ B 级证据，无 D 级单独通过 | 每条 AC ≥ C 级证据，无 D 级单独通过 | 禁止转换到归档，必须补充证据 |
| 独立验证 | 子代理已执行，无未处理的推翻项 | 跳过（LITE 允许更高信任度） | STANDARD/HEAVY 禁止转换到归档 |
| 对抗性测试 | 每条 AC ≥ 2 个测试维度 | 跳过 | STANDARD/HEAVY 禁止转换到归档 |

插入时机：SKILL.md「阶段完成闸门」在 7-验收阶段转换到归档前检查。gate_check.py 以 `--stage 7 --check completion` 触发。

## 2. LITE 安全场景 [safety]

LITE 不可跳过的 3 种场景（即使 LITE 也必须走完整闸门）：
1. 涉及安全相关代码（认证/授权/加密/数据隔离）
2. 改动跨 ≥3 个模块的公共接口
3. 包含数据迁移或数据格式变更

## 3. 角色约束规则 [role]

| 角色 | 首要原则（必须保护） | 禁止（绝对不做） |
|---|---|---|
| 产品经理 | 需求忠实于用户意图 | 写实现代码、改技术设计 |
| 技术经理 | 架构一致性 | 设计阶段写实现代码；审查阶段自己改代码 |
| 项目经理 | 需求完整传递到任务 | 改需求内容、改技术设计 |
| 开发员 | 功能对齐 DESIGN.md | 改 REQUIREMENT/DESIGN、跨任务改动 |
| 测试员 | 用例忠实于 REQUIREMENT AC | 自己修代码、删除/弱化失败用例 |
| 运维 | 部署安全性与可回滚性 | 改业务代码、未经审查直接部署 |

## 4. 阶段反模式速查 [antipattern]

> 完整反模式清单见 `references/anti-patterns.md`（每条有原子化 id，可脚本化检查）。
> 以下为 SKILL.md 原内联摘要，供快速自检。

### 3-开发 反模式
> 锚点：每行改动追溯到需求
- 在 TASK.md write_files 范围外修改文件（scope creep）
- 引入 DESIGN.md 未规划的新依赖
- 硬编码本应配置化的值（端口/URL/密钥）
- 跳过错误处理"因为场景太简单不会出错"
- 在 LITE 模式下合并多个 task 的改动到一个 commit

### 4-测试 反模式
> 锚点：按验收标准写用例，不改实现
- 只测 happy path，跳过边界和异常
- 测试代码与实现代码紧耦合（mock 过深导致测试失去价值）
- 删除或弱化失败的测试用例而非修复实现
- 测试依赖执行顺序（用例间有隐式依赖）

### 5-审查 反模式
> 锚点：0 问题才过关（所有级别）
- 只审查自己写的代码（违反独立性）
- 审查同时修改代码（违反技术经理红线）
- 跳过跨模块影响分析（"只改了一个文件"）
- 审查报告只有"通过"无具体检查记录

### 跨阶段 可执行性反模式
> 锚点：输出必须可执行
- AC 含"优化/改进/提升"但无量化标准（cross-04）
- 技术决策含"合适的/适当的"但无具体选型（cross-05）
- 阶段完成输出缺少具体下一步动作（cross-06）

## 5. 疤痕协议 [scar]（信息性扫描，不阻塞）

> 借鉴 Meta_Kim 疤痕协议。完整定义见 `references/scars.md`。

适用：所有复杂度扫描疤痕。STANDARD/HEAVY 写入新疤痕，LITE 仅评估不写入。

| 检查项 | 条件 | 缺失时 |
|--------|------|--------|
| 疤痕扫描 | 0-需求步骤 0A 已执行（读取 `.specs/scars/` 并匹配） | 信息性，不阻塞 |

疤痕写入时机：7-验收步骤 6A（评估是否写入）、热修流程步骤 7A（强制评估）。
