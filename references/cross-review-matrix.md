# 交叉评审规范 — 6 维矩阵 + 子代理协议

> 所有阶段交叉评审的统一定义。各阶段文件只需引用本文件，不在内部重复定义。

---

## 总览

flow-go 有 3 套 6 维评审矩阵，分别用于文档层（阶段 0/1/2）、代码层（阶段 3）、质量层（阶段 5）。

| 评审类型 | 适用阶段 | 评审对象 | 产出位置 |
|---------|---------|---------|---------|
| 文档评审 | 0-需求 / 1-设计 / 2-任务 | 阶段工件（REQUIREMENT/DESIGN/TASK） | `<change-id>-REVIEW.md` |
| 代码评审 | 3-开发 | 单任务代码改动 | `<task-id>-SUMMARY.md` 交叉评审章节 |
| 质量评审 | 5-审查 | 全量代码改动 | `REVIEW.md` |

---

## 矩阵 A：文档评审（阶段 0/1/2）

每个维度 PASS/FAIL 判定，6 维全 PASS 才通过。

| 维度 | 判定标准 | FAIL 信号 |
|------|---------|-----------|
| 上游一致性 | 产出工件与上游输入（用户意图/上游工件）逻辑对齐 | AC 无法追溯到用户需求；设计与需求矛盾 |
| 下游充分性 | 下游阶段能仅凭此工件开始工作 | 设计缺少足够细节供任务拆解；任务缺少足够细节供开发 |
| 用户意图对齐 | 工件内容未偏移用户原始表述 | 引入了用户未提到的功能/约束；技术决策与业务动机脱节 |
| 完备性 | 无空值/占位符/TODO/TBD；所有必要章节已填写 | 有"待定"/"TODO"占位符；关键章节为空 |
| 反幻觉 | 引用的库/API/模块/配置真实存在且可验证 | 引用了不存在的包名；虚构了用户未提到的约束 |
| 范围控制 | 无隐性扩展/过度设计/实现泄露 | 需求文档包含技术方案；设计超出需求范围；任务冗余 |

### 各阶段侧重

| 维度 | 0-需求侧重 | 1-设计侧重 | 2-任务侧重 |
|------|----------|----------|----------|
| 上游一致性 | 用户意图 vs AC 对齐 | DESIGN vs REQUIREMENT AC 覆盖 | task action/done vs DESIGN |
| 下游充分性 | 设计阶段能否从此开始 | 任务拆解能否从此开始 | 开发员能否仅凭 task 编码 |
| 用户意图对齐 | AC vs 用户原话有无偏移 | 技术方案 vs 用户原始需求 | 任务覆盖 vs 用户需求 |
| 完备性 | 无空值/占位符 | 架构图+API+ADR+风险+对齐 | verify+依赖无环+粒度 |
| 反幻觉 | 无虚构需求/引用存在 | 引用的库/API/模块真实存在 | verify 路径/文件真实存在 |
| 范围控制 | 无隐性扩展/实现泄露 | 无过度设计/无超出范围 | 无遗漏/无冗余/并行合理 |

## 矩阵 B：代码评审（阶段 3-开发）

单任务级别的交叉评审，验证实现质量。

| 维度 | 判定标准 | FAIL 信号 |
|------|---------|-----------|
| 规格合规 | 实现 vs TASK action/done + DESIGN 一致 | 功能与 task action 描述不符；遗漏 task done 条件 |
| 设计对齐 | 实现路径遵循 DESIGN 方案，偏离有说明 | 使用了 DESIGN 未选定的技术方案；绕过了架构约束 |
| 测试证据 | verify 输出真实 + 文件齐全 | verify 输出只有"通过"无真实命令输出；verify 命令未实际执行 |
| 边界卫生 | diff 无越界 + 无无关改动 | 改了 TASK write_files 之外的文件；夹带了与任务无关的变更 |
| 反幻觉 | 无虚构 import/API/配置 | import 了不存在的模块；调用了不存在的 API；配置了不存在的服务 |
| 质量底线 | 无 bug/无密钥/无空 catch/无技术债标记 | 有明显的逻辑 bug；硬编码了密钥/token；catch 块为空；有 TODO/FIXME/HACK/XXX 标记；有被注释掉的代码块；硬编码临时值（测试 URL/mock 数据/占位符） |

---

## 矩阵 C：质量评审（阶段 5-审查）

全量代码级别的 6 维 + 安全审查。

| 维度 | 判定标准 | 修复要求 |
|------|---------|---------|
| R1 认知过载 | 单函数 > 50 行 / 嵌套 > 3 层 | 拆分函数或降低嵌套 |
| R2 变更传播 | 任务无关文件被改动 | 回退越界变更 |
| R3 知识重复 | 同逻辑粘贴 2+ 处 | 提取共用函数 |
| R4 偶然复杂 | 抽象层级超过实际需要 | 简化为直接实现 |
| R5 依赖混乱 | 业务层 import 基础设施实现 | 调整依赖方向 |
| R6 领域扭曲 | 变量名用技术词而非领域词 | 使用领域语言命名 |

安全审查（与 R1-R6 并行）：`git diff --staged | grep -i "api_key\|token\|secret\|password"` + OWASP 快查。

## 子代理调用协议

### 调用规范

主代理 dispatch 交叉评审子代理时，必须构造以下 prompt 结构：

```
你是 flow-go 交叉评审审查者。你对工件执行 6 维矩阵检查。

## 你的任务
评审类型：{文档评审/代码评审/质量评审}
评审对象：{具体工件名称}
评审矩阵：见下方矩阵定义

## 输入工件
{工件内容，完整贴出}

## 上游工件（供一致性检查）
{上游工件内容，如 REQUIREMENT.md 供设计评审参考}

## 评审矩阵
{从本文件复制对应矩阵的完整表格}

## 输出格式
严格使用以下 Markdown 格式：

### 评审矩阵
| 维度 | 结果 | 说明 |
|------|------|------|
| {维度1名} | PASS/FAIL | {如 FAIL，写明具体问题和位置} |
| {维度2名} | PASS/FAIL | ... |
...（6 维全部列出）

### 发现问题
- Critical（置信度 ≥90）：
  - {文件:位置 — 问题描述 — 置信度 — 建议修复方向}
- Important（置信度 80-89）：
  - {文件:位置 — 问题描述 — 置信度 — 建议修复方向}
- {全 PASS 则写"无"}

## 约束
- 只评审给你看的内容，不猜测未提供的工件
- FAIL 必须给出具体位置和修复方向，不允许模糊描述
- 不要修改任何文件，只产出评审报告

## 置信度评分
对每个潜在问题评分 0-100：
- 0-49：低置信度，大概率误报或不重要
- 50-79：中置信度，真实问题但不关键
- 80-89（Important）：高置信度，确认的真实问题
- 90-100（Critical）：极高置信度，必须修复

**仅报告置信度 ≥80 的问题。** 过滤掉低置信度发现以减少噪音。
```

### 子代理压缩输出契约

当主代理处于 caveman/ultra 模式时，子代理输出启用压缩契约：

**探索子代理格式**：
```
path:line — symbol — ≤15字说明
...
totals: N 文件, M 匹配
```

**审查子代理格式**：
```
path:line 置信度% 维度: ≤20字问题. ≤20字修复.
```

**契约遵从规则**：
- 禁止完整句子（用片段）
- 禁止解释性前缀（"我发现"/"建议修改"）
- 每发现 ≤ 一行
- 全 PASS 时输出 `0 issues`

### 各阶段调用参数

| 阶段 | 评审类型 | 传入工件 | 上游工件 | 子代理 model |
|------|---------|---------|---------|-------------|
| 0-需求 | 文档评审 | CHANGE.md + REQUIREMENT.md | 用户原始输入 + CONTEXT.md | sonnet |
| 1-设计 | 文档评审 | DESIGN.md | REQUIREMENT.md + CHANGE.md + CONTEXT.md | sonnet |
| 2-任务 | 文档评审 | TASK.md | DESIGN.md + REQUIREMENT.md | sonnet |
| 3-开发 | 代码评审 | git diff + TASK + DESIGN + SUMMARY | DESIGN.md | sonnet |
| 5-审查 | 质量评审 | git diff + 全部 SUMMARY | REQUIREMENT.md + DESIGN.md | sonnet |

### 子代理约束

- 子代理使用**全新上下文**（不继承主代理对话历史）
- 子代理**只读不写**（产出评审报告由主代理写入文件）
- 子代理**无轮数限制**（文档层），但主代理有 3 轮上限（代码层）
- 子代理 dispatch 时指定 **model: sonnet**（探索/评审任务不需要最强模型）
- 每个发现必须附带置信度评分（0-100），仅输出 ≥80 的发现

## 失败处理策略

### 子代理输出异常

| 异常类型 | 检测方式 | 处理 |
|---------|---------|------|
| 输出为空 | 评审报告长度 < 50 字符 | 重试一次（同一上下文），仍为空 → 主代理自行完成评审，记录"子代理异常，主代理兜底" |
| 格式错误 | 评审矩阵表格缺少行或列 | 解析可用部分，缺失维度由主代理补充评审 |
| 维度判定缺失 | 6 维中 < 6 维有明确 PASS/FAIL | 缺失维度由主代理补充评审 |
| 内容幻觉 | 评审引用了未提供的文件/内容 | 该维度判定作废，主代理重新评审该维度 |

### 重试策略

- **文档评审**（阶段 0/1/2）：无轮数上限，修文档后重新 dispatch，直到 6 维全 PASS
- **代码评审**（阶段 3）：最多 3 轮（修代码 + re-verify + re-dispatch），超过 3 轮 → 停下报告用户
- **质量评审**（阶段 5）：循环评审直到所有级别 = 0（无硬性上限），但超过 3 轮仍有问题 → 停下报告用户

### 降级策略

当子代理连续 2 次输出异常时，主代理可切换为**自评审模式**：
1. 主代理按同一矩阵自行评审
2. 在评审报告中标记"⚠️ 自评审模式（子代理异常）"
3. 自评审结果与子代理结果享有同等效力（闸门认可）
